## 0. 一句话架构

**phi-agent 是一套「微内核 + 插件」的 Agent 运行时，它被编译成一个可移植的内核，能在桌面 / 移动 / 服务端任一端独立运行；每个运行着的内核实例叫「节点」；外壳（UI）通过统一传输附加到节点上，因此同一套 UI 既能连本机节点，也能连别的设备上的节点。**

用一句话回答「它长什么样」：**一堆能力各异的节点，每个节点里住着一个极小的内核和一群插件，外壳浮在节点之上。**

## 2. 分层与依赖规则

| 层 | 职责 | 依赖允许指向 | 可否移除 |
|---|---|---|---|
| **Shell 外壳** | 呈现与输入 | 内核公开的命令/事件接口 | ✅ 可（无头节点就是没有外壳） |
| **Plugins 插件** | 一切领域功能 | 内核、端口 | ✅ 可（这是设计的核心） |
| **Kernel 内核** | 机制：总线、注册、生命周期、机制性端口 | 无（只依赖基础库） | ❌ 不可，但必须极小；**无领域词汇** |
| **Ports 机制性端口** | 存储/事件日志、传输、时钟、ID、日志、配置 | 无 | ❌ 不可（定义在内核） |
| **Ports 领域端口** | `ModelPort`、`MemoryPort`、`SandboxPort`… | 无 | ✅ 可（定义在**所属领域的契约包**，内核不认识） |
| **Domain 领域** | 纯逻辑（循环/策略算法） | 端口 | ✅ 可（在插件内） |
| **Adapters 适配器** | 平台实现 | 端口 | ✅ 可（换实现/换平台） |

**依赖方向铁律**（对应 P8）：箭头只能向内。出现逆向依赖或环，CI 失败。

## 3. 七大关键架构决策 ⭐

> 每一条都写清：面临的选择、取向、放弃了什么。真正难逆、且是取舍的，另立 ADR。

### 决策 1：微内核 + 插件，还是可裁剪的单体？

- **选项 A · 可裁剪单体**：一个完整应用，编译期用 feature flag 开关功能。简单、快，但「删一个模块」要重编译，且模块间容易隐式耦合，P10 天然难达标。
- **选项 B · 微内核 + 插件**：内核极小，一切功能是可增删的插件。灵活、可热插拔，代价是引入注册表、生命周期、间接层，开发复杂度略高。
- **取向**：**B。** 因为你的第 1 号要求就是「模块随时增删改」，选项 A 从根上不满足。代价（间接层）用「内核 API 预算」控制，不任其膨胀。

### 决策 2：事件溯源，还是 CRUD 状态？

- **选项 A · CRUD**：直接读写当前状态。直观、简单，但难回放、难换端、难审计。
- **选项 B · 事件溯源**：状态 = 事件折叠。可回放、可复制、天然支持换端与审计，代价是存储增长、读模型维护、最终一致。
- **取向**：**在会话/运行主线上用 B，其余用 A（混合）。** 主线的可回放与换端是刚需；配置类数据没必要事件化。

### 决策 3：插件用什么语言/形态写？

- **选项 A · 原生（Rust/C++）**：最强最快，但**不可移植**、**不安全**、**难热卸载**、作者门槛高。
- **选项 B · WASM（Component Model）**：可移植、隔离好、可细粒度撤权，但 TS→WASM 工具链不友好、门槛高、生态窄。
- **选项 C · TypeScript（内嵌 JS 引擎）**：作者门槛最低、与 UI 同语言、生态最大、全端可移植；代价是 JS 比原生慢、引擎沙箱弱于 WASM。
- **取向**：**C 为默认代码档，配「性能逃生舱」**——性能敏感的插件**自带原生 CLI（独立进程）**，逻辑仍用 TS 写、重活交给原生二进制。三档为：**声明式（零代码）→ TypeScript（默认代码）→ 原生（含自带 CLI，仅桌面/服务端）**；WASM 降为可选档。这让插件**「好写」与「够快」同时成立**，也是「Minecraft 级广度」与「跨三端」的落地方式。

### 决策 4：协同用单写者，还是多写者 CRDT？

- **选项 A · 单写者 + attach**：一个会话由一个节点写，其他端只读+发命令。简单、无冲突，但「多端同时编辑」做不到。
- **选项 B · 多写者 CRDT**：任意端可写，自动合并。灵活，但复杂、难调试，且 Agent 事件流（有严格因果）用 CRDT 语义存疑。
- **取向**：**v1 用 A；B 留作预留 R2。** 你说的「只支持最基础的协同（选执行位置）」正是 A。R1（换端）用「所有权转移」实现，也不需要多写。

### 决策 5：共享内核用 Rust，还是 TypeScript？

- **选项 A · TS 内核**：与现有 Solid UI 同语言，单语言栈、迭代快；服务端跑 Node/Deno。代价是移动端后台执行、原生能力、性能、单二进制分发较弱。
- **选项 B · Rust 内核**：一对三端（Tauri 2 覆盖桌面+移动，服务端是同一个内核编译的原生二进制）；性能与原生能力强；HTTP/SQLite/WASM 生态成熟；和现有 `src-tauri` 脚手架一致。代价是与 UI 跨语言边界（用 Tauri IPC / 统一传输），团队需熟悉 Rust。
- **取向**：**B（已定 2026-11-08，ADR-0003）**。理由：三端一套内核是 F2 的最直接实现，且 `agent-research` 对原生宿主的判断也偏向 Rust 宿主内核。

> **不再「待确认」**。此前本文标注「倾向 B，但列为待确认」，与 `open-questions.md` 的「已定」不一致——现统一为已定，落 ADR-0003。

### 决策 6：UI 内置，还是 UI 也是插件？

- **选项 A · UI 内置**：UI 与内核同仓库、紧耦合。简单。
- **选项 B · UI 作为外壳插件**：UI 通过统一的命令/事件接口接入；第三方可贡献 UI 面板/命令。代价是需要一层 UI 扩展模型。
- **取向**：**B（但 UI 本身是「默认外壳」而非第三方插件）。** 因为「换端」要求同一套 UI 能连不同节点——UI 与内核解耦是 F3 的前提；同时它让 UI 也能被扩展（Minecraft 式）。

### 决策 7：内核边界怎么划？可缺席的模块如何保证安全？ ⭐

> 这是原设计中最严重的自相矛盾（「内核」一词同时承担「机制层」与「承载 Run/预算」两种含义，六份文档 vs 三份文档对撞）。完整论证见 ADR-0009。

- **选项 A · 单一「内核」概念**：内核既含机制、也含 Run 骨架与预算记账。简单，但领域词汇泄进机制层（违反 P1/P8），且「移除任意模块」无法验收。
- **选项 B · 内核狭义化 + 发行基线 + 必需槽位**：内核只含机制（无领域词汇）；`Run/Step/预算/策略/沙箱/模型网关` 全在插件；官方发行声明「必需槽位（能力契约）」与「基线插件（必装但可换实现）」。
- **取向**：**B。** 并且：
  - **不引入「广义内核」这个说法**——那等于把刚拆开的两个概念又粘回去。
  - 必需槽位缺失 → 进入 `Maintenance` 模式（**不拒绝进程启动**，否则用户没有修复入口）。
  - 运行中丢失安全组件 → 进入 `Degraded` 模式，**禁止发起新的副作用动作**。
  - **安全能力缺失一律拒绝，不降级为放行**（策略/沙箱/审批任一不可用 → 有副作用动作 `deny`）。

```
   内核（机制）        发行基线（必装插件，仍是插件）          可选插件
   ┌─────────┐        ┌──────────────────────────┐       ┌───────────┐
   │ EventBus│◀───────│ loop/session/policy/     │       │ 第三方工具 │
   │ Registry│        │ sandbox/approver/model-gw│       │ 技能/UI/… │
   │Lifecycle│        │ store/…（可换实现）       │       │           │
   │ 机制端口 │        └──────────────────────────┘       └───────────┘
   └─────────┘        缺失 → Maintenance / Degraded       缺失 → 明确降级
     无领域词汇          无特权代码路径（同一套扩展点）
```

## 4. 运行时全景（多端拓扑示意）

```
        桌面端（Tauri 桌面壳）             手机端（Tauri 移动壳）
        ┌──────────────────────┐          ┌──────────────────────┐
        │ 外壳  ⇄  节点 A       │          │ 外壳  ⇄  节点 B       │
        │ (本地全功能内核)       │          │ (本地全功能内核)       │
        └─────────┬────────────┘          └─────────┬────────────┘
                  │                                 │
                  │      可选协同（v1：attach；R1：换端）│
                  └──────────────┬──────────────────┘
                                 │ 统一传输（进程内 / WS / HTTPS）
                  ┌──────────────▼──────────────────┐
                  │  服务端节点 C（常开，无头或 Web 控制台）│
                  │  · 重活丢给它跑                     │
                  │  · 可作为 attach 目标 / 换端目标     │
                  │  · 不是必须的中心（本地优先 P4）      │
                  └──────────────────────────────────┘

  关键：A、B、C 是**对等**的节点，能力可不同（手机 CPU 弱、服务器常开）。
        「协同」= 外壳 attach 到别的节点，或把 Run 所有权交给别的节点。
        没有「谁必须在线」，因为每个节点都能单独运行。
```

## 5. 质量属性 → 架构机制映射

> `awesome-architecture` 的功课：每个质量属性都要落到具体机制上，不能只喊口号。

| 质量属性 | 靠什么机制保证 |
|---|---|
| **可扩展 / 可移除**（最高优先） | 微内核（P1）+ 端口 Null 实现 + 事件解耦（P3）+ 「禁用模块启动」冒烟测试（P10） |
| **可移植（三端一套内核）** | 端口-适配器（P2）+ 内核不依赖平台 API + TS 插件（内嵌 JS 引擎） |
| **离线可用 / 数据主权** | 本地事实源（P4）+ 同步为可选层 + 密钥走 OS Keychain / 等效加密 |
| **安全 / 可控** | 能力中介（P5）+ 策略插件 + 沙箱 + 预算上限 + 事件留痕 |
| **可观测 / 可回放** | 事件日志（P3）+ 步骤级 trace |
| **可测试性** | 端口 Null 实现 + 事件可重放 + 纯领域逻辑 |
| **性能** | 内核热路径薄；重活可下沉到服务端节点；缓存与模型路由 |

## 6. 演进：MVP → 成长 → 成熟

> `awesome-architecture` 反复强调：**别拿成熟期的图去套 MVP。** 但本项目的细节功能未定，这里只给「架构骨架」的演进，功能演进待补。

| 阶段 | 架构长什么样 | 该操心什么 |
|---|---|---|
| **MVP** | 单进程节点（内核 + 内置外壳 + 发行基线插件）；无同步；事件日志只落本地 | 内核边界是否真干净（无领域词汇）；必需槽位/运行模式是否成立；P10 冒烟是否跑通；**能否完成一次真实编码任务** |
| **v1** | 内核与插件分离为独立制品；TS 插件 ABI（内嵌 QuickJS + iframe 隔离）上线；服务端节点可用；局域网 attach；插件可安装 | 插件 API 版本化；跨端一致性；成本与限额；确定性测试进 CI |
| **成熟期** | 多层插件（声明式/TS/原生+自带 CLI）；多 Agent；换端 R1、状态复制 R2、团队节点 R3；插件市场 | 安全边界、向后兼容、多租户、持续评测 |

> 交付边界的完整定义见 `80-roadmap/evolution.md`。
