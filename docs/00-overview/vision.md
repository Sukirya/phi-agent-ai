# 愿景、定位与非目标

> 状态：🌿 · 最后更新：2026-11-08

---

## 1. 一句话定位

**phi-agent 是一个「本地优先、多端协同」的 Agent 客户端：每个设备都能独立跑完整的 Agent，也能把任务放到别的设备上跑；数据默认留在本地，协同是可选的增强而非前提。**

它和两类东西的区别：

- 和**云端 Agent 产品**（ChatGPT / Claude 网页版）的区别：**数据与执行默认在本地**，离线可用，用户拥有自己的会话、记忆与密钥。
- 和**单个桌面 Agent 应用**（Claude Code / Cursor）的区别：**多端是一致的**——桌面、移动、服务端跑的是同一个内核，任务可以在端之间流转。

---

## 2. 为什么做它：要解决的痛点

| 痛点 | 现状 | phi-agent 的回答 |
|---|---|---|
| **数据不在自己手里** | 会话、记忆、密钥都在厂商云上 | 本地优先：事实源在设备本地，同步可选 |
| **离线就废** | 断网即不可用 | 完整功能离线可用（除依赖远端模型的部分） |
| **多设备割裂** | 手机上开的任务电脑上接不上；每个端各是一套 | 同一内核、同一会话模型，端之间可 attach / 流转 |
| **能力被厂商锁死** | 工具、模型、界面都改不了 | 微内核 + 插件：模型、工具、技能、界面皆可替换 |
| **动起来的 Agent 不受控** | 一旦能动手就难审计、难刹车 | 策略 + 沙箱 + 审批 + 预算上限是**发行基线的一等公民**（见 ADR-0009） |

> 核心信念（与 `awesome-architecture` 一脉相承）：**能力是模型给的，安全与可控是架构给的。**

---

## 3. 目标用户与场景

用户在**多个设备**上工作，且在意**数据主权**与**可定制**。典型场景：

1. **个人多设备**：台式机、笔记本、手机、家里的小服务器。在手机上发起的任务，可以在电脑上继续看/接管；重活丢给常开的服务器节点。
2. **隐私敏感**：会话与记忆不想上传到第三方；模型 Key 自己出，或接本地模型。
3. **深度定制**：想换模型、加自己的工具、写自己的技能、改界面——而且希望这些改动**即插即用、可随时撤掉**。
4. **团队/自托管**（预留，非 v1）：一台自建服务器作为团队共享节点。

---

## 4. 核心价值主张（三条）

1. **Own it** —— 数据、密钥、执行默认都在你自己的设备上；用什么模型、装什么插件由你决定。
2. **Anywhere** —— 同一个 Agent，换个设备接着用；执行位置可选。
3. **Extensible to the bone** —— 内核极小，其余全是插件；任何模块都可被删除、替换或新增而不破坏系统。

---

## 5. 功能 vs 质量：两类需求分开看

> 借鉴 `awesome-architecture` 的基本功：**先分清「系统要能做什么」（功能）和「系统要做得多好」（质量属性）。**

### 5.1 功能性需求（当前已知的高层能力，细节待补）

| 编号 | 能力 | 说明 | 详设状态 |
|---|---|---|---|
| F1 | **基础 Agent 能力** | Agent 行动循环、工具调用、技能（skills）、上下文组装 | 见 `40-runtime/` |
| F2 | **多端独立运行** | 桌面 / 移动 / 服务端均可单独跑完整 Agent | 拓扑见 `10-architecture/overview.md` |
| F3 | **基础协同：选择执行位置** | 用户可指定会话/任务在哪台设备上执行，其他端 attach 查看与控制 | 见 `50-distributed/` |
| F4 | **多 Agent** | 多 Agent 协作完成任务；另有「辅助模型」做权限审批 | 见 `40-runtime/agent-loop.md`、`40-runtime/policy-and-approval.md` |
| F5 | **插件系统** | 广度对标 Minecraft 的 Mod/Plugin：可加内容、可改行为、可换实现 | 见 `30-extension/plugin-system.md` |

> **F4 的阶段注记**：多 Agent 的**架构预留**在 v1 就位（执行树 `parentRunId`、`strategy.orchestration` 扩展点、Task 树、深度与扇出上限），但**实现不作为 v1 硬门槛**——先做单层主从，再扩展。理由与交付边界见 `80-roadmap/evolution.md`。

> **刻意留白**：F1–F5 的具体形态（哪些工具、什么样的协同交互、审批策略长什么样）**尚未确定**，后续由你提供。架构必须能在**不知道这些细节**的前提下成立——这正是「不要写死功能性需求」的含义：**设计的是接缝（seam）与契约，不是功能本身。**

### 5.2 预留（非 v1，但架构要留门）

| 编号 | 能力 | 说明 |
|---|---|---|
| R1 | **任务换端继续（handoff）** | 进行中的 run 连同检查点迁移到另一台设备继续执行 |
| R2 | **会话状态复制** | 多端同时持有一份会话副本，最终一致 |
| R3 | **团队共享节点** | 一台服务器作为多人共享的运行节点（多租户边界） |

> 预留不等于现在实现。架构上要保证 R1–R3 **不需要推翻 F1–F5 就能加上**。

### 5.3 质量属性（我来取舍，见 `10-architecture/overview.md` §5 与 `70-quality/`）

初判优先级（**可推翻**）：

| 质量属性 | 目标倾向 | 理由 |
|---|---|---|
| **可扩展 / 可移除** | 极高 | 你的第 1 号要求，是项目的差异点 |
| **可移植（多端一套内核）** | 高 | F2 的前提 |
| **离线可用 / 数据主权** | 高 | 定位的核心 |
| **安全 / 可控** | 高 | Agent 能「动手」，必须能刹车 |
| **可观测 / 可回放** | 中高 | 多步黑盒，没有 trace 无法调试 |
| **性能（延迟/吞吐）** | 中 | 单机为主，先够用，不做极致优化 |
| **易用性** | 中 | 取决于最终形态，暂不设死指标 |

## 6. 非目标（明确不做，防止范围蔓延）

- ❌ **不是一个托管云服务**。phi-agent 不做「帮你托管 Agent 的 SaaS」；服务器端只是「你自己的一台设备」。团队共享是预留项，不是 v1 目标。
- ❌ **不绑定某个模型厂商**。模型是插件/配置，不是内核的一部分。
- ❌ **不绑定某一类 Agent**（不是只做编码 Agent，也不是只做通用助手）。内核只认「Agent 定义 / 工具 / 技能」这些抽象，具体是什么 Agent 由配置和插件决定。
- ❌ **不做极致性能**。单设备本地场景优先；大规模并发、亿级用户不是本项目的关注点。
- ❌ **不在 v1 做完整的多写者实时协同**（如多人同时编辑同一会话）。v1 只做「选择执行位置 + attach」，多写复制是 R2。

---

## 7. 关键约束（不可逾越的边界）

- 🔴 **内核必须极小且稳定**。内核一旦膨胀，扩展性就死了。这是第 1 号要求的技术底线。
- 🔴 **Agent 会出错、会跑偏、会烧钱**。循环必须有不收敛的兜底（步数/成本/超时/重复检测）。
- 🔴 **工具调用有副作用且不可逆**。必须有审批、沙箱、最小权限。
- 🔴 **提示注入是头号威胁**。一切外部内容（工具返回、检索结果、网页）当**不可信输入**。
- 🔴 **跨端一致性天然是分布式的**。多端 = 部分失败、无全局时钟——不能假装它不存在。
- 🟡 **单人/小团队开发**。架构不能沿用需要大团队维护的重型方案（微服务、K8s、多仓等）。这也反向支持「微内核 + 单体内核」。

---

## 8. 已确认的决策（见 `00-overview/open-questions.md`）

1. 协同拓扑：**对等节点**（服务器是可选对等节点，不是必经中继）—— ADR-0004。
2. 内核语言：**Rust 内核 + TypeScript 外壳**，插件以 TS 为主 —— ADR-0003 / ADR-0005。
3. v1 优先端：**桌面 → 服务端 → 移动**；移动完整支持不作 v1 门槛，但技术验证提前。
4. 默认形态：**编码 Agent 优先**（只影响首批插件与示例，不影响架构）。
5. 内核边界：**狭义内核 + 发行基线 + 必需槽位** —— ADR-0009；安全权威与审批绑定 —— ADR-0010；换端以 Session 为单位 —— ADR-0011。
