# 架构原则

> 状态：🌿 · 最后更新：2026-11-08

这些原则是**不可动摇的设计约束**。任何设计、任何代码、任何插件，违反了原则就是错的——哪怕它能跑通。评审时逐条对照。

> 之所以叫「原则」而不是「建议」：需求会变、模块会增删，唯有一小组稳定原则能让系统在变化中不散架。这与 `awesome-architecture` 说的「架构是长出来的，但地基不能动」一致。

---

## 原则一览

| 编号 | 原则 | 一句话 |
|---|---|---|
| **P1** | 微内核 | 内核极小且稳定，其余皆为插件 |
| **P2** | 端口-适配器 | 领域逻辑只依赖接口，不依赖平台 |
| **P3** | 一切皆事件 | 状态变化即事件，事件日志是事实源 |
| **P4** | 本地优先 | 默认本地、离线可用；同步是增强 |
| **P5** | 能力安全 | 显式声明权限，最小授权，全部经中介 |
| **P6** | 数据驱动优于代码 | 能声明就别编码 |
| **P7** | 可组合优于集成 | 小而正交、按需拼装 |
| **P8** | 依赖方向单向 | 依赖只能向内，禁止环 |
| **P9** | 契约版本化 | 一切跨边界契约都带版本与能力协商 |
| **P10** | 可移除性 | 可选模块都能被删掉而不破坏内核；安全能力缺失必须拒绝 |

---

## P1 · 微内核

**是什么**：内核（kernel）只负责**最少且最稳定**的机制——事件总线、服务/能力注册表、生命周期、以及**机制性端口**（存储/事件日志、传输、时钟、ID、日志、配置）。**其余一切**（Agent 循环、工具、技能、记忆、模型、策略、沙箱、UI）都是注册进内核的**插件**。

**为什么**：你的第 1 号要求是「扩展性极强，一个模块随时被删改或添加」。只有当内核不承载任何具体功能时，功能才能被随意增删。内核越大，可移除性越差。

**怎么落地（可检验）**：
- 内核代码里**不得出现**任何领域词汇（如 `Session`、`Run`、`Tool`、`Memory`）——只有 `Plugin`、`Registry`、`EventBus`、`Port`。
- **领域端口不在内核里**：`ModelPort`、`MemoryPort`、`SandboxPort` 等由**所属领域的契约包**定义，内核不认识它们。内核只保留机制性端口与事件日志端口（总线要落盘，日志端口必须离得足够近）。
- 内核的公开 API 表面积应被**显式预算**（例如：核心 trait/interface 数量有上限，超出需要 ADR）。
- 新增功能的默认路径是「写一个插件」，而不是「改内核」。

**反例**：把「工具调用」写进内核 —— 那么「不要工具」的部署就做不到，P10 立刻失败。
**反例**：把 `Run`/`Step`/预算记账写进内核 —— 领域词汇泄进机制层，P1 与 P8 同时失败。它们属于**运行时骨架插件**（见 P10 与 ADR-0009）。

## P2 · 端口-适配器（Hexagonal）

**是什么**：领域逻辑（Agent 循环、策略判定等）只依赖**端口（port，即接口）**：`StoragePort`、`TransportPort`、`ModelPort`、`SandboxPort`、`ClockPort`…。具体的实现是**适配器（adapter）**：SQLite / 内存 / 远端；进程内 / WebSocket；Anthropic / OpenAI / 本地模型。

**为什么**：同一个内核要跑在桌面、移动、服务端三种环境，平台差异必须被适配器吸收，不能渗透进领域逻辑。这也是 P10「可移除」的基础——换掉一个适配器不触碰内核。

**怎么落地**：
- 领域层**不 import** 任何平台 API（文件系统、网络、UI、具体数据库驱动）。
- 每个端口至少有**两个实现**证明它可替换：一个真实实现 + 一个内存/Null 实现（Null 实现同时让 P10 的可移除性可测；但 Null 必须诚实，见 P10——只读可返回空，写不得假装成功）。
- 端口定义在「谁来用谁定义」处（依赖倒置）。

**反例**：Agent 循环里直接 `fs::write(...)` —— 那移动端沙盒、远端执行、可测试性全部受损。

## P3 · 一切皆事件

**是什么**：系统的状态变化以**事件（event）**表示并追加到**事件日志（journal）**。当前状态 = 对事件的折叠（fold）。事件是**不可变、有序、可持久、可复制**的。

**为什么**：一次给足四样东西——
- **可回放/可审计**：每一步（思考、工具调用、结果）都能重放，对照 `agent-research` 的「多步黑盒必须 trace」。
- **本地优先**：事件日志天然适合离线积累与后续同步（P4）。
- **换端继续（R1）**：迁移一个 run = 迁移它的事件与检查点。
- **可移除**：子系统通过**订阅事件**解耦，删掉一个订阅者不影响发布者。

**怎么落地**：
- 写操作是「追加事件」；读操作是「从物化的读模型读」。
- 事件的唯一真相是日志；任何从日志可推导的缓存都是**派生物**，可随时丢弃重建。
- 事件带 **schema 版本**（P9），旧事件永远可读。

**注意（取舍）**：事件溯源有成本（存储增长、读模型维护、最终一致）。本系统**不要求所有状态都事件溯源**——只在**会话/运行**这条主线上强制，配置类数据可用普通关系表。在哪条线用、哪条线不用，见各子系统文档与 ADR。

## P4 · 本地优先

**是什么**：数据默认存**本地**，读写**不依赖网络**；跨端同步是**可选增强**，不是运行前提。断网时，除「调用远端模型」这类天然需要网络的能力外，功能照常。

**为什么**：这是定位的核心。也是「多端独立运行」的技术前提——如果每台设备都依赖一个中心，那它就不是「能单独运行的端」。

**怎么落地**：
- 每个节点有完整的**本地事实源**（本地日志 + 本地存储，见 P2）。
- 同步是**显式的可插拔层**，不是内核默认假设：拓扑可以为「无同步 / attach / 复制 / 换端」四档（见 `50-distributed/topology-and-sync.md`）。
- 任何「必须联网才能用」的设计都要给出明确理由，并降级到本地可用。

**反例**：启动时先向服务器拉取会话列表 —— 违反本地优先，且引入单点失败。

## P5 · 能力安全（Capability-based Security）

**是什么**：一切能「改变世界」的动作（文件、网络、进程、花钱、发送）都经过**能力中介**。插件/Agent 必须**显式声明**它需要哪些能力，内核按最小授权原则发放，并全程可审计。

**为什么**：Agent 的危险不在「说错」，在「改坏、泄露、花钱」。这既是安全要求，也是「插件系统能大胆开放」的前提——只有权限被中介，才敢让第三方插件跑。

**怎么落地**：
- 能力是**显式的、可列举的、可撤销的令牌**，不是隐式继承的权限。
- 一切副作用经**策略引擎（Policy）**判定 → `allow / deny / ask / modify`，判定结果作为事件留痕。
- 外部内容（工具返回、检索结果、网页）一律**不可信输入**，不得直接提升权限（防提示注入）。

## P6 · 数据驱动优于代码

**是什么**：只要能用**声明**表达，就不要用**代码**。Agent 定义、技能、策略、插件清单、工具 schema、UI 布局——优先是数据（manifest / DSL），而非硬编码。

**为什么**：声明式的东西可以被**加载、校验、热更新、被第三方提供**而不需要改内核（P1）、不需要重编译。这正是 Minecraft 的**数据包（datapack）**思路：加内容 = 丢一个 JSON，而不是改引擎。它直接服务于 P10。

**怎么落地**：
- 新增「一类内容」时，先问：能不能用一个**新的 manifest 类型**表达？
- 声明有 **schema** 与**校验**，非法声明在加载期报错，不污染运行时。

**反例**：「支持 X 工具」就写一段 Rust —— 应该是一个工具 manifest + 一个可选的 TS 实现。

## P7 · 可组合优于集成

**是什么**：功能做成**小而正交**的单元，通过注册与订阅**按需拼装**；而不是把功能塞进一个大而全的模块。

**为什么**：可组合是 P10 的前提——只有单元够小、耦合够低，才能单独移除。这与 `skills/` 的哲学（「小而可组合、可被 hack」）同源。

**怎么落地**：
- 一个插件只做一件事；「什么都做」的插件是反模式。
- 单元之间通过**事件**（P3）或**能力注册表**通信，不直接持有彼此引用。
- 优先组合既有的扩展点，而不是新造扩展点（对齐 `skills/SCOPE.md`「能由现有能力组合出来的，就不新增」）。

## P8 · 依赖方向单向

**是什么**：依赖只能朝**内核**方向流动：`UI/插件 → 端口 ← 适配器`；领域逻辑不依赖外层。**禁止环依赖**。

**为什么**：依赖方向是「可移除」的结构保证。一旦出现环，删任何一个模块都会牵动另一个。

**怎么落地**：
- 用分层规则约束：Shell/UI → Plugin → Port(接口) ⇆ Adapter，Domain 只依赖 Port。
- 依赖检查可以（也应该）进 CI：出现逆向依赖或环即失败。

```
        ┌──────────────────────────────────────────┐
        │  Shell / UI            (可替换、可移除)     │
        └───────────────┬──────────────────────────┘
                        │ 依赖
        ┌───────────────▼──────────────────────────┐
        │  Plugins (工具/技能/循环/记忆/策略/…)       │
        └───────────────┬──────────────────────────┘
                        │ 依赖
        ┌───────────────▼──────────────────────────┐
        │  Ports (接口)  ←  Domain (领域逻辑)         │   ← 依赖倒置点
        └───────────────▲──────────────────────────┘
                        │ 实现
        ┌───────────────┴──────────────────────────┐
        │  Adapters (SQLite/SQLCipher、WS、模型…)    │
        └──────────────────────────────────────────┘

  规则：箭头只能向下/向内核；Domain 永不依赖 Adapter 与 Shell。
```

## P9 · 契约版本化

**是什么**：一切**跨边界**的契约——插件 API、事件 schema、工具 schema、同步协议、UI 扩展点——都带**版本号**，并支持**能力协商**（consumer 声明所需，内核解析，缺则降级）。

**为什么**：扩展性强的系统，插件与内核**各自独立演进**。没有版本化，任何一方升级都会炸掉另一方。这是「模块随时增删改」在时间维度上的要求。

**怎么落地**：
- 插件在其 manifest 里声明 `apiVersion` 与所需能力；内核按语义化版本匹配。
- 事件 schema 演进遵循「只增不改、旧事件永可读」。
- 破坏性变更 = 新版本 + 兼容层 + ADR，绝不原地改语义。

## P10 · 可移除性与安全降级（本项目的「一票否决」测试）

**是什么**：先把模块分成两类，再分别断言：

| 类别 | 断言 |
|---|---|
| **可选模块** | 移除后系统仍能启动；**不依赖它的功能一切照常**，依赖它的功能**明确不可用**，或按契约**安全降级** |
| **必需槽位**（required slot） | 某个**能力契约**的位置（策略判定、沙箱执行、模型调用、持久化…）必须被某个实现占据。必需的是**契约**，不是具体插件——实现可替换 |

**P10 的断言只对可选模块成立。** 对必需槽位，断言改为：**缺失时拒绝进入正常执行模式**——绝不是静默放行、也绝不是「无隔离地照常跑」。

**为什么**：「任意模块都能删掉而一切照常」在物理上不成立——删掉模型网关后不可能还照常调用模型。原来那句话把「可移除」和「可缺席」混为一谈，导致降级表写出「沙箱缺席 → 无隔离运行」这种与安全文档直接冲突的结论。分开之后：**可扩展性说的是「能换、能组合」，不是「能跑到什么都没有」。**

**怎么落地（可检验规则）**：

- 任何模块对外只通过**端口/事件**暴露能力；对该模块的引用必须是**可选**的。
- 每个端口都有 **Null 实现**，但 Null 必须**诚实**：
  - **只读端口**可以返回空集（「没有记忆」是合法状态）。
  - **写端口不得返回「成功」**（假装写入成功 = 数据丢失，比崩溃更糟）。
- **安全相关槽位（策略 / 沙箱 / 审批）缺席时，有副作用的动作一律 `deny`。** 显式豁免只能由用户作为独立管理操作给出，不能由模型、技能或待执行工具请求隐式触发。
- 启动时必需槽位缺失 → 进入 **`Maintenance` 模式**（仅诊断、安装插件、修复配置），**不拒绝进程启动**——否则用户连修复入口都没有。
- 运行中丢失安全组件 → 立即进入 **`Degraded` 模式**，禁止发起**新的**副作用动作。
- CI 里保留一组「禁用模块 X 后启动 + 关键用例」的冒烟测试。
- **新功能上线的动作** = 注册一个插件；**下线的动作** = 注销它。不存在「半拆」的模块。

**反例清单（会被这条测试挡下）**：
- 内核直接 `new ToolRegistry()` —— 删掉工具子系统后内核引用悬空 ❌
- 插件 A 直接 `const B = require('./pluginB')` —— 删掉 B 会让 A 崩 ❌
- 沙箱不可用时「无隔离跑，靠策略兜底」 ❌ —— 策略兜底也是一种放行（见 P5）
- 持久化端口用「写成功」的 Null 实现顶上 ❌ —— 数据静默丢失

> **一句话记住 P10**：*如果删掉它系统就起不来，那它就不该被内联依赖；如果它是安全能力，那缺了它就要拒绝做事。*

> 发行基线（官方必装的一组插件）与必需槽位清单见 ADR-0009。基线插件**仍是普通插件**，走同一套扩展点 API，**没有特权代码路径**——差别只写在发行清单里。

## 原则冲突时怎么裁

原则之间偶尔会打架（例如 P3 事件溯源 vs 简单性）。裁决顺序：

1. **P5 的安全下限不可交换**：任何「不确定」都收敛到拒绝或找人，不收敛到放行。P10 不能拿它换可移除性——「沙箱没了就无隔离跑」不是可移除，是漏洞。
2. **P10（可移除性）> 其余**：对**可选模块**，不可移除的设计一票否决。
3. **P4（本地优先）**：与网络相关的取舍，本地优先胜。
4. **P5（安全）与便捷性冲突时，安全胜**（可提供显式豁免机制，但默认安全）。
5. 其余冲突交 ADR 记录取舍，不靠直觉。
