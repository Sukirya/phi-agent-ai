# 插件系统与扩展点

> 状态：🌿 · 最后更新：2026-11-08
> 上游：ADR-0001（微内核）、ADR-0005（插件三档）、原则 P1/P5/P6/P9/P10
> 关联：`10-architecture/module-map.md`（模块清单）

本文回答：**「一切皆插件」到底怎么落地？** 这是本系统「可移除性」的地基——扩展点的形状定了，其余子系统的接口才有形状可依。

---

## 1. 设计目标与张力

| 目标 | 来源 |
|---|---|
| **广度**：能加内容、能改行为、能换实现、能加界面 | F5「对标 Minecraft 的 Mod/Plugin」 |
| **可移植**：一个插件尽量三端通用 | F2 / ADR-0003 |
| **安全**：第三方插件不得为所欲为 | P5 |
| **可热插拔**：随时加载/卸载/替换，不重启不崩 | P10 |
| **可独立演进**：插件与内核各自升级不互相炸 | P9 |
| **好写**：插件以 TypeScript 为主，门槛低 | ADR-0005 |

**核心张力**：广度 ↔ 安全 ↔ 可移植。三者不可兼得，故用 **ADR-0005 的三档 ABI** 分层化解——按插件所需能力选择最安全的那一档。

---

## 2. 插件是什么

**插件 = 一个带清单（Manifest）的可加载单元，它向若干扩展点（Extension Point）贡献内容（Contribution）。**

三句话界定了整个系统：

- **内核不实现功能**，只提供机制（总线/注册表/生命周期）。
- **功能 = 一组内置插件**（不是内核的一部分）。内置与第三方插件走**同一套**扩展点 API——没有「亲儿子特权路径」。这是可移除性的关键：内置插件也必须是可拔的。
- **插件之间不直接引用**，只通过事件或注册表协作（`module-map.md` 规则 R2）。

> 设计检验：**如果某个内置功能无法作为插件加载，那它就不该内置。**

## 3. 三档 ABI + 性能逃生舱（回顾 ADR-0005）

```
                       插件需要什么？
                            │
        ┌───────────────────┼───────────────────┐
        │                   │                   │
   只是「声明内容」       需要「逻辑」         需要「OS 能力 / 极致性能」
   （定义/技能/策略/        （算法/工具执行）      （文件/进程/设备集成；重活）
    UI 布局/工具 schema）                        │
        │                   │                   │
        ▼                   ▼                   ▼
   ┌─────────┐         ┌──────────┐        ┌──────────────┐
   │ T0 声明式│         │ T1 TypeScript│    │ T2 原生       │
   │ 零代码   │         │ 内嵌JS引擎  │        │ 进程内库/自带CLI│
   │ 全端·最安全│        │ 全端·引擎沙箱│        │ 分端·需白名单   │
   └─────────┘         └──────────┘        └──────────────┘
   默认档                默认代码档            桌面/服务端；永不进移动端
                              │
                              │ 实测不够快？
                              ▼
                    ┌────────────────────────────┐
                    │ 性能逃生舱：自带原生 CLI/守护进程│
                    │ 插件用自己的包附一个二进制，     │
                    │ 经 process.exec 调用（独立进程）│
                    │ 桌面/服务端；需声明能力+策略放行 │
                    └────────────────────────────┘
```

**核心主张**：**插件逻辑一律用 TypeScript 写**（内核侧与 UI 侧同一个语言，门槛最低）；**性能敏感的部分自带原生 CLI** 来兜底。WASM 降级为可选档 T1′（非 TS 语言或最强进程内隔离，按需再引入）。

**选择准则（写进 review 清单）**：能 T0 就别 T1；T1 够快就别 T2；只有确需 OS 能力或 T1 实测不够快，才用 T2 / 自带 CLI。每升一档都要在清单里写明理由。

### 3.1 性能逃生舱：自带 CLI / 守护进程 ⭐

> 这是「插件用 TS，但要够快」的答案：**逻辑写 TS，重活交给插件自己打包的原生二进制。** 不是提高 JS 引擎性能，而是把性能敏感的部分换出语言。

**何时用**：索引构建、代码解析/编译、大文件处理、加密、图像/音视频、GPU 等 JS 引擎明显吃力的场景；或需要用到某个只有原生的库。

**两种形态**：

| 形态 | 说明 | 适用 |
|---|---|---|
| **一次性 CLI** | 插件调用一个短命子进程，stdin/stdout 交换 JSON | 单次重活（解析一个文件、跑一次编译） |
| **守护进程** | 长驻子进程 + 本地 IPC（socket/管道），保持热状态 | 反复调用（代码索引、语言服务） |

**机制要点**：

- **打包**：二进制放在插件包 `bin/<target-triple>/`，按平台分包；清单 `cli:` 指向它。
- **调用**：经 `process.exec:<插件自己的二进制>` 能力；**只允许执行包里那个二进制**，参数有白名单/校验；交换格式用 JSON（CLI）或本地 socket RPC（守护）。
- **隔离**：它是**独立进程**，天然可套 `provider.sandbox`（进程沙箱/容器），并设 CPU/内存/超时限额——比进程内插件更易隔离。
- **生命周期**：随插件的 `activate` 启动、`deactivate` 终止；崩溃由宿主重启或降级，不影响内核。
- **平台矩阵**：✅ 桌面 / 服务端；❌ 移动端（系统限制 + 安全），移动端只能 T0/T1。
- **信任**：二进制是插件包的一部分，信任级别等同于该插件；进市场时需签名/校验。

**为什么不干脆全用 T2？** 因为绝大多数插件逻辑不重，写 TS 最快、最好维护、全端可跑；只有少数重活需要原生。**「TS 写胶水 + CLI 做重活」让两者各司其职。**

## 4. 插件清单（Manifest）

一切插件的统一声明。清单本身是 **T0 数据**，先于代码被解析与校验（P6）。

```yaml
# plugin.yaml —— 插件清单示例
id: com.example.git-tools          # 全局唯一
name: Git Tools
version: 1.2.0                     # 插件自身版本（语义化）
apiVersion: "1"                    # 依从的内核/扩展点契约大版本（P9）
platforms: [desktop, server]       # 省略 = 全端
cli: ./bin/git-tools               # 可选：自带 CLI/守护进程（性能档，仅桌面/服务端）

permissions:                       # 声明所需能力（P5），内核按最小授权发放
  - fs.read:${workspace}
  - fs.write:${workspace}
  - process.exec:./bin/git-tools   # 只允许执行自带的这个二进制
  - net.http: ["api.github.com"]
  - event.subscribe: session:<self>  # 有作用域的权限：默认只能订阅本插件相关的事件

parts:                             # 一份插件可拆成多个 part，各自有独立的 contributes / requirements
  - part: backend                  # 后端部件：跑在节点上
    tier: ts                       # declarative | ts | native
    entry: ./dist/backend.js       # T0 省略；T1 指向 TS 编译产物(js)；T2 指向原生库
    contributes:                   # 向哪些扩展点贡献什么
      - point: provider.tool
        id: git.commit
    activation:                    # 懒激活，避免启动即加载一切
      - on: capability.requested
        capability: tool.git.commit
      - on: startup                # 少数必须的插件才用
    requirements:                  # 对内核/扩展点契约的版本要求
      kernel: ">=1.0 <2.0"
      extensionPoints:
        provider.tool: ">=1"

  - part: ui                       # UI 部件：跑在外壳里
    tier: ts
    entry: ./dist/ui.js
    contributes:
      - point: ui.panel
        id: git-panel
    requirements:
      extensionPoints:
        ui.panel: ">=1"

limits:                            # 运行限制（宿主强制）
  memory: 64MB
  cpuMs: 5000
  timeout: 30s
```

**校验时机**：加载期（Load）严格校验——`tier` 与 `entry` 是否匹配、`platforms` 是否包含当前端、`apiVersion` 是否兼容、`permissions` 是否是已知能力、`contributes` 指向的扩展点是否存在。**事件订阅是「有作用域的权限」，默认只能订阅本插件相关的事件**（见 §5 F 表），不是无限制的全局订阅。**非法清单在加载期报错并跳过，绝不污染运行时。**

### 4.1 部件（part）与前后端拆分

- 一份插件可声明**多个 part**，每个 part 有自己的 `contributes` 与 `requirements`（如 `part: backend` 跑在节点、`part: ui` 跑在外壳）。
- 某个 part 的扩展点在某端不存在 → **只跳过该 part，不跳过整个插件**。headless 节点没有 `ui.*` 扩展点，工具部分照常加载。
- 远程 attach 时，UI part 的资源从**节点**获取（节点托管插件包并做版本匹配），不要求客户端本地安装该插件；版本按 `apiVersion` 协商。

## 5. 扩展点目录 ⭐

> 这是全系统最值钱的一张表。**能扩展什么，系统就能变成什么。** 每个扩展点是一个带版本的契约。

扩展点按「贡献什么」分六类。标记 **🔒** 的是**安全扩展点**：普通插件对它们**只能收紧、不能放宽**（ADR-0010）。

### A · 内容型（T0 即可）

| 扩展点 | 契约（贡献什么） | 示例 |
|---|---|---|
| `content.agentDefinition` | 一个 Agent 定义（角色/提示/工具/预算） | 「代码评审 Agent」 |
| `content.skill` | 一个技能包（清单 + 指令 + 资源） | 「提交规范」技能 |
| `content.policyRule` 🔒 | 一组策略规则 | 「写工作区外文件需审批」——**只能加严，不能覆盖用户限制** |
| `content.toolSchema` | 一个有 schema、无执行体的工具声明 | 声明式工具（执行体由别处提供） |
| `ui.layout` | 一段 UI 布局/命令声明 | 工具栏按钮 |

### B · 算法/策略型（T1 TypeScript）

| 扩展点 | 契约 | 说明 |
|---|---|---|
| `strategy.loop` | 行动循环策略 | ReAct / plan-execute / reflexion，内核不内置任一种 |
| `strategy.orchestration` | 多 Agent 编排 | supervisor / group-chat / pipeline |
| `context.contributor` | 向上下文注入内容 | 注入项目规则、注入检索结果 |
| `strategy.modelRouter` | 模型路由策略 | 简单任务给小的、复杂给大的 |
| `retrieval.strategy` | 记忆/检索策略 | 混合召回 + 重排 + 置信门控 |
| `judge.policyEvaluator` 🔒 | 策略判定逻辑 | allow/deny/ask/modify 的规则求值（**只能收紧**） |
| `judge.approver` 🔒 | 审批者实现 | **人 / 辅助模型**（小模型审批在此实现）；**提供某工具的插件不得审批该工具** |

> **替换安全实现需要用户的显式信任**：`provider.sandbox`、`judge.policyEvaluator`、`judge.approver` 的实现可以换（换容器、换判定算法），但这是**独立的管理操作**——不能由模型、技能或待执行工具请求隐式触发；替换后仍不能绕过宿主能力校验、预算与审计入口。

### C · 能力提供型（T0/T1）

| 扩展点 | 契约 | 说明 |
|---|---|---|
| `provider.tool` | 工具的执行体 | 一个可调用能力（读文件、调 API…） |
| `provider.model` | 模型来源适配 | Anthropic / OpenAI / 本地模型 |
| `provider.sandbox` 🔒 | 沙箱执行后端 | 进程 / 容器 / 远端（按端选择档位） |
| `provider.memoryBackend` | 记忆的存储后端 | SQLite / 向量库 / 远端 |
| `provider.mcpServer` | MCP 工具来源 | 接入外部 MCP（经防腐层翻译 schema） |

### D · 边界适配型（多为 T2 或内核内置适配器）

| 扩展点 | 契约 | 说明 |
|---|---|---|
| `adapter.storage` | 存储实现 | SQLite / 内存 / 远端（也用于测试） |
| `adapter.transport` | 传输实现 | 进程内 / WS / HTTP |
| `adapter.searchIndex` | 检索索引实现 | 向量 + BM25 双通道 |

### E · 界面型（TS 侧 · **内嵌模型**，见下文 §5.1 与 `60-frontend/multi-frontend.md`）

| 扩展点 | 契约 | 说明 |
|---|---|---|
| `ui.view` | 一个视图，占据某**区域** | 会话视图、记忆浏览器、文件树、插件管理页 |
| `ui.panel` | 侧栏/工具面板 | Git 面板、检索面板 |
| `ui.command` | 一个命令 | 可被用户或模型触发（含命令面板） |
| `ui.keybinding` | 键位绑定 | |
| `ui.contextMenu` | 上下文菜单项 | |
| `ui.statusItem` | 状态栏项 | 当前模型、预算剩余 |
| `ui.renderer.message` | 自定义消息渲染 | 富文本、卡片 |
| `ui.renderer.toolResult` | 自定义工具结果渲染 | diff、表格、图表、运行日志 |
| `ui.decoration` | 消息/条目装饰 | 徽章、内联动作按钮 |
| `ui.settings` | 设置页 | 插件自己的配置界面 |
| `ui.theme` | 主题令牌 | 颜色/间距/字体变量 |
| `ui.region` | **插件自定义新区域**，供其他 UI 插件填充 | 让 UI 本身可递归扩展 |

### 5.1 UI 扩展模型（内嵌、非独立窗口）⭐

> **硬约束**：插件 UI **一律内嵌**在外壳的布局树中；**外壳独占窗口，插件不创建独立窗口**（不用 OS 级新窗口、不用 `window.open`）。「浮动/弹层」是**应用内图层**，不是独立窗口。

**外壳定义区域（Region），插件向区域贡献视图**：

```
┌───────────────────────────────────────────────────────────┐
│ region.header      顶栏（模型选择、预算）                    │
├──────────┬────────────────────────────────────┬───────────┤
│ sidebar  │  region.main                        │ sidebar   │
│  .left   │  主内容（会话视图 / 备用工作区）        │  .right   │
│ 记忆/文件 │   ┌──────────────────────────────┐  │  Git/检索  │
│          │   │ region.inline                 │  │           │
│          │   │  消息内联：diff/图表/按钮       │  │           │
│          │   └──────────────────────────────┘  │           │
├──────────┴────────────────────────────────────┴───────────┤
│ region.statusbar      底栏（状态项）                         │
└───────────────────────────────────────────────────────────┘
         ↑ 之上叠加（仍在同一窗口内）
   region.overlay   应用内浮层（命令面板、提示、下拉）
   region.modal     应用内模态层（设置、审批对话框）
```

**两档实现**（精神和插件三档一致：能声明就别写代码）：

| 档 | 形态 | 安全/可移植 | 适用 |
|---|---|---|---|
| **D · 声明式 UI**（默认） | 插件产出**声明式视图树**（组件 + 数据绑定），外壳渲染 | 高：不碰 DOM、自动适配主题与响应式、跨端一致 | 面板、表单、列表、设置页、状态项 |
| **C · 代码 UI**（强大档） | 插件提供**沙箱化组件代码**，在隔离渲染环境里跑，经宿主桥访问数据与命令 | 中：更强自由，需隔离与能力中介 | 复杂交互视图、自定义渲染器 |

**关键规则**：
- **布局归外壳所有**：插件贡献的是布局树里的**节点**，不是窗口。外壳决定区域尺寸、响应式与主题。
- **经宿主桥访问内核**：插件 UI 只能「读事件流、发命令」，**不直接触碰内核状态**（对齐 P5）。它看到的与会话视图看到的是同一条事件流。
- **UI 扩展点必须版本化**（P9）：区域、桥 API、视图 schema 都带版本。
- **跨端自适应**：同一份声明式视图在桌面/移动上由外壳重排；插件无需为每种端写 UI。

**已定**：C 档用「**受控组件协议 + 虚拟树**」——插件产出视图树，外壳渲染；插件不直接操作 DOM；复杂/第三方渲染场景回退 iframe 内嵌（仍在同一窗口内）。见 ADR-0007。

### 5.2 UI 代码的执行隔离 ⭐

> 回应一个常见误解：**受控组件协议只解决了渲染接口，没解决代码执行隔离。** 本文明确后者的边界。

- **硬约束**：C 档插件 UI 代码**不得与宿主同执行环境运行**。D 档（声明式视图树）本来就没有代码，安全。
- **C 档两条实施路径**：
  1. **iframe**：`sandbox="allow-scripts"`，**不得**加 `allow-same-origin`；源为 `app://plugin/<pluginId>` 或一次性 blob URL。
  2. **内嵌 JS 引擎渲染进程**（若实现）。
- **宿主桥鉴权**：桥接走 `postMessage`/`MessagePort`，每次调用携带**宿主签发的短期 capability token + Principal**；宿主侧再校验插件 id、能力、会话作用域。插件拿不到宿主全局对象。
- **通信只能是消息**：无共享内存、无同步调用、无 DOM 访问。

> **「iframe 回退档」不是「降级到不安全」**，而是**另一种隔离实现**——只要不加 `allow-same-origin`，它同样满足「不与宿主同执行环境」。

### F · 拦截/钩子型（中间件）

| 扩展点 | 语义 | 能否阻断 |
|---|---|---|
| `event.subscribe` | **按作用域**被动观察（`session:<id>` / `project:<id>` / 本插件自身）；默认不能观察其他插件的事件 | 否 |
| `mw.beforeModelCall` | 模型调用前（改提示/短路） | 可 |
| `mw.beforeToolInvoke` | 工具调用前（改参数/拒绝） | 可 |
| `mw.afterToolInvoke` | 工具返回后（改结果/脱敏） | 可 |
| `mw.beforePolicyDecision` 🔒 | 策略判定前（**只能加严**） | 可 |
| `mw.beforeContextAssemble` | 上下文组装前（裁剪/注入） | 可 |

> **中间件与事件订阅的区别**：事件是「事后通知」（不能改结果）；中间件是「链上的一环」（可改、可阻）。二者都用，各司其职。

> **关键事件**（审批、预算、策略、换端）只能由所属模块产生，生产者身份由宿主附加；插件发布的事件带 `producer`，不能伪装成这些事件。

## 6. 贡献与注册

```
插件加载 → 内核读清单 → 校验 → 按 contributes 逐项注册
                                   │
                     ┌─────────────┴──────────────┐
                     ▼                            ▼
             注册到扩展点注册表            记入能力表（permissions→granted）
                     │
                     ▼
       其他模块通过注册表查询：「有没有人贡献 strategy.loop？」
                     │
              有 → 用；没有 → 用 Null 实现（降级，不崩）   ← P10 的关键
```

**注册表是类型化的**：每个扩展点有明确的贡献类型；注册时校验类型，防止张冠李戴。

### 6.1 选择与组合语义

类型正确之外，多份贡献「怎么选、怎么排」由下表约定：

| 扩展点类别 | 语义 | 多贡献时 |
|---|---|---|
| 单实例（`strategy.loop`、`strategy.orchestration`、`strategy.modelRouter`） | 同时只能有一个生效 | 用户选择 / 显式默认；冲突不自动裁决 |
| 多实例（`provider.tool`、`provider.model`、`provider.memoryBackend`、`content.skill`、`ui.*`） | 全部并存 | 按 id 唯一；**同名冲突 = 加载期报错** |
| 链式（`context.contributor`、`mw.*`） | 按显式顺序执行 | 贡献者声明 `order`；相同 order 位置未定义即报错 |
| 动态扩展点（`ui.region`） | 插件自定义新区域 | **schema 由外壳提供**，插件只能实例化，不能定义契约 |

> 类型化注册表只保证类型正确，**不代替**选择/排序/冲突规则。

## 7. 生命周期

```
discover → resolve → validate → grant → activate → (run) → deactivate → unload
 发现      解析依赖    校验清单   授权    注册贡献            注销贡献    释放资源
```

| 阶段 | 做什么 | 可移除性含义 |
|---|---|---|
| discover | 扫描插件目录/市场 | 新增插件 = 丢文件 |
| resolve | 解析 `requirements`（内核/扩展点版本） | 版本不兼容 → 跳过并提示，不崩 |
| validate | 严校清单 | 非法 → 跳过 |
| grant | 按 `permissions` 发放能力令牌 | 未声明的能力拿不到（P5） |
| activate | 注册 `contributes` | 激活即「上线」 |
| deactivate | 注销贡献、断开事件订阅 | 卸载一个插件 = 注销它 |
| unload | 释放内存/句柄 | 无「半拆」状态 |

**懒激活**：清单里的 `activation` 决定何时激活（如「有人要用它的工具时」），避免启动即加载全部。这是 Minecraft 的「按需加载 mod」思路。

### 7.1 热卸载与在途工作

卸载不是「删掉文件」，而是分四步的安全退出：

```
停止接受新调用 → 等待/取消在途调用 → 保留旧版本直到引用清零 → 注销贡献并释放资源
```

- **在途范围**：工具调用、等待审批、事件回调、CLI 子进程、引用其实现的进行中 Run。
- **已有 Run 引用该插件的工具**：**不强制中断**，按检查点记录「依赖缺失」，恢复时进入待核对；或由用户选择取消。
- **进程内 T2 原生库限制热卸载**：只能标记停用、进程退出时释放；**不得声称可安全热卸载**。
- **卸载失败要有清理规则**（残留句柄、子进程孤儿）——避免「半拆」状态。

## 8. 隔离与能力安全

- **T1 插件跑在内嵌 JS 引擎的沙箱里**（无隐式系统调用、无直接文件/网络句柄）；只能通过宿主提供的**能力接口**触碰外界。
- **自带的 CLI 是独立进程**：走 `process.exec` 能力 + 进程级沙箱（`provider.sandbox`），比进程内插件更易隔离；只允许执行**插件自己包里**的那个二进制，且仅桌面/服务端。
- **能力令牌**由内核按清单发放，是**显式、可列举、可撤销**的（P5）。未声明的能力调用 = 直接失败。
- **一切副作用经策略中介**：即便插件声明了 `fs.write`，具体某次写仍需过 `plugin-policy`（可能被 `ask`）。
- **外部内容不可信**：插件/工具返回的内容，不得直接提升权限（防提示注入）。
- **T2 进程内原生插件与宿主同地址空间，持有宿主权限**——它是特权档，必须白名单 + 用户显式同意，不是「快一点的普通插件」。

```
  插件（不可信） ──请求 fs.write:/x──▶ 内核能力层 ──令牌校验──▶ 策略判定 ──▶ 适配器执行
                    （无令牌 = 拒）      （无声明 = 拒）     （可 ask 人类/辅助模型）
  插件（TS） ──process.exec:./bin/x──▶ 能力层 ──只允自带二进制──▶ 进程沙箱 ──▶ 子进程
```

---

## 9. 版本化与能力协商（P9）

- 每个**扩展点契约**有版本；插件在 `requirements.extensionPoints` 声明所需范围。
- 内核按**语义化版本匹配**：不满足 → 该插件跳过（不是全局失败）。
- 事件与工具 **schema 只增不改、旧版永可读**。
- **破坏性变更 = 新扩展点版本 + 兼容层 + ADR**，绝不原地改语义。

## 10. 插件之间：不直接引用（R2 的结构保证）

```
  ❌ 禁止：plugin-A 直接 use plugin-B            → 删掉 B 会崩 A
  ✅ 允许：plugin-A 查询注册表 use strategy.loop  → 没有则降级
  ✅ 允许：plugin-A 发布事件，plugin-B 订阅它     → 删任一方都无碍
```

若两个插件要协作，正确姿势是：**一方贡献到某扩展点，另一方通过注册表/事件使用它**——把「点对点依赖」换成「面向扩展点的协作」。

## 11. 分发与信任

| 渠道 | 说明 | 信任级别 |
|---|---|---|
| 本地目录 | 用户手动放置 | 用户自担 |
| 内置 | 随内核发布 | 受信（但仍是可移除插件） |
| 市场（预留） | 签名 + 来源验证 | 依签名与权限声明 |

**签名与来源验证**是市场的前置条件（预留），v1 不强制。**但能力声明与授权从 v1 就要有**——因为它是安全的地基，后补代价极高。

## 12. 端到端示例：加一个「Git 提交」工具

```
1. 目录：plugins/git-tools/plugin.yaml + dist/plugin.js  (+ 可选 bin/git-tools 自带 CLI)
2. 清单：tier: ts；permissions: [fs.rw:${workspace}, process.exec:./bin/git-tools]
3. contributes:
     - point: provider.tool, id: git.commit       # 提供工具执行体
     - point: ui.panel, id: git-panel             # 提供界面面板
4. activation: on capability.requested: tool.git.commit   # 用到才加载
5. 用户对话 → 循环决定调用 git.commit
6. 内核：查注册表得执行体 → 策略判定（写工作区？ask 人类/辅助模型？）
7. 插件（TS）调用自带 CLI（独立进程，沙箱内执行）→ 结果成为事件追加进日志 → UI 渲染

- 卸载该插件 → 注销两个贡献 → 工具与面板消失，系统照常      （P10 ✅）
- 未声明 process.exec → 第 7 步调用被拒，插件无法越权        （P5 ✅）
```

## 13. 关键决策与权衡

| 决策 | 取向 | 放弃了什么 |
|---|---|---|
| 内置功能也走插件 API | 是 | 「亲儿子捷径」的便利，换来一致性与真可移除 |
| 三档 + 性能逃生舱（ADR-0005） | 保留 | 单一 ABI 的简单，换来广度/安全/可移植的平衡 |
| **插件以 TypeScript 为主** | 是 | 原 WASM 方案的强隔离，换来最低的编写门槛与最大生态 |
| **性能靠自带 CLI 兜底**（非提高 JS 引擎性能） | 是 | 全端纯 TS 的一致性，换来重活的原生性能（限桌面/服务端） |
| 懒激活 | 是 | 启动即一切就绪的简单，换来启动速度与资源 |
| 插件间不直接引用 | 强制 | 直接调用的便利，换来可移除性 |
| 能力声明从 v1 起 | 是 | 先用后补的速度，换来安全地基 |
| **UI 内嵌、不建独立窗口**（ADR-0006） | 是 | 插件自定义窗口的自由，换来布局/主题/跨端一致 |
| **UI 双档（声明式 / 代码）** | 是 | 单一 UI 模型的简单，换来安全与强大的兼顾 |
| **安全扩展点只能收紧**（ADR-0010） | 是 | 改写安全策略的灵活性，换来不可绕过 |
| **事件订阅有作用域** | 是 | 全局观察的便利，换来插件间隔离 |
| **前后端按 part 拆分** | 是 | 单清单的简单，换来 headless / 远程 attach 与前后端的独立加载 |

## 14. 反模式

- ❌ **内核里直接 `new XxxManager()`** → ✅ 通过扩展点注册，缺则 Null 实现（P10）。
- ❌ **插件 A 直接引用插件 B** → ✅ 注册表/事件协作（R2）。
- ❌ **为了省事把内置功能写进内核** → ✅ 内置也是插件。
- ❌ **扩展点无版本** → ✅ 每个扩展点带版本 + 能力协商（P9）。
- ❌ **插件声明权限 = 直接授权** → ✅ 声明 ≠ 放行；每次副作用仍过策略（P5）。
- ❌ **一个大而全的插件** → ✅ 小而正交，用组合而非打包（P7）。

## 15. 与 P10 的关系（验收）

插件系统就是 P10 的实现载体：

```
移除插件 P  →  注销其全部贡献  →  其他模块查注册表得到「无」  →  用 Null 实现降级  →  系统照常
```
