## 0. 一句话

**一切能「改变世界」的动作，都必须先过策略引擎拿到许可，才允许执行。** 策略输出四选一：`allow / deny / ask / modify`；`ask` 交给**审批者**——人或**辅助模型**（小模型）。

> 这是「能力是模型给的，安全是架构给的」的落点。也是让第三方插件能大胆开放的前提：**只有副作用被统一中介，才敢让陌生代码跑。**

---

## 1. 三层概念（不要混）

| 层 | 回答的问题 | 载体 |
|---|---|---|
| **能力 Capability** | 这个插件/工具**被允许碰什么** | 清单声明 + 内核发放的令牌 |
| **策略 Policy** | 这一次动作**该不该放行** | 规则引擎 → 决策 |
| **沙箱 Sandbox** | 放行后**在哪里执行** | 隔离环境 |

**关系**：能力是「静态授权」（能碰什么），策略是「动态判定」（这次要不要拦），沙箱是「执行隔离」（跑在哪）。**三者缺一，安全不成立。**

---

## 2. 能力模型（静态）

- 插件/工具在清单里声明 `requires`（如 `fs.rw:${workspace}`、`net.http:["api.x.com"]`、`process.exec:./bin/x`）。
- 内核按**最小授权**发放**能力令牌**（显式、可列举、可撤销）。
- **未声明的能力调用 = 直接失败**（不是「再问你」）。
- 能力是**作用域化**的：`fs.read:${workspace}` 只给工作区，不是整个磁盘。

---

## 3. 策略引擎（动态）

### 3.1 规则模型（`judge.policyEvaluator` 扩展点）

| 字段 | 说明 |
|---|---|
| `id`, `priority` | 优先级决定命中顺序 |
| `matcher` | 匹配：动作类型 / 工具 / 资源 / 上下文（如「工作区内 vs 外」） |
| `effect` | `allow / deny / ask / modify` |
| `rationale` | 可读理由（进审计） |

### 3.2 默认与冲突

- **默认拒绝（least privilege）**：无规则命中 → `deny`（fail-safe）。
- **冲突**：`priority` **只在层内**决定规则命中顺序；**跨层取交集**，不是「最高优先级者胜」。见 §3.4。
- **`modify` 的语义**：不直接放行，而是**改写动作**（如把「写任意路径」收紧为「写工作区」、把危险参数剔除）后重新判定。**`modify` 只能收紧，不能放宽。**

### 3.3 决策流程（热路径）

```
工具调用请求 ──▶ 能力令牌校验（未声明？→ 拒）
                      │ 通过
                      ▼
                冻结动作摘要（ActionDigest：主体/节点/资源/toolId@version/参数/cwd）
                      │
                      ▼
                策略规则求值（分层，取交集）──▶ allow ──▶ 执行前复核 ──▶ 沙箱执行
                      │                                          │
                      │                              权限已撤销？审批已过期？
                      │                              资源与摘要不一致？→ 重新判定
                      ├── deny ──▶ 拒绝（事件留痕）
                      ├── modify ─▶ 改写动作 → 重新冻结摘要 → 重新求值
                      └── ask ──▶ 交审批者（绑定 actionDigest）
```

**决策全程同步**（阻塞该次调用），结果落 `PolicyDecisionMade` 事件——**每个副作用恰好有最终决策**（`I-6-2`）。

### 3.4 安全权威：普通插件只能收紧 ⭐（ADR-0010）

> 「谁有权改安全规则」此前无人回答：规则、求值器、审批者、沙箱、策略前置中间件全是扩展点，插件与内置走同一套 API，而规则又按最高 `priority` 生效——于是第三方插件可以提交一条更高优先级的 `allow` 来覆盖用户限制。修正如下：

```
      宿主能力（能碰什么）  ∩  用户授权（允许什么）  ∩  当前有效策略（这次放不放）
                     ∩
      普通插件贡献的规则 / 中间件  ← 只能收紧，不能放宽
```

- **最终允许范围 = 三层交集**。任何一层拒绝，最终就是拒绝。
- 普通插件**不能**靠提高 `priority` 覆盖用户限制；**不能**自行注册一个审批者来批准自己的请求。
- **利益冲突**：提供某工具的插件，**不得**贡献审批该工具的审批者实现。
- 用户**可以**修改默认规则，或**显式信任并替换**策略/沙箱/审批实现——但这属于**独立的管理操作**，不能由模型、技能、待执行工具请求**隐式**完成。
- 替换后的实现仍不能绕过**宿主能力校验、预算与审计入口**。

## 4. 审批者（Approver）

**审批者是 `judge.approver` 扩展点的实现，两种并列**：

| 审批者 | 说明 | 权限 |
|---|---|---|
| **人类** | 应用内弹窗/面板（内嵌，非独立窗口，ADR-0006） | 全部 |
| **辅助模型**（小模型） | 无状态判定器：输入「动作 + 上下文 + 风险」，输出「批准 / 驳回 / **升级给人**」+ 理由 | **受限**（见 §5） |

**审批请求是实体**：`ApprovalRequest{ status: Pending/Approved/Rejected/Expired, actionDigest, riskProfile, approverKind, expiresAt }`——**绑定冻结后的动作摘要**（见 §5.1）。

---

## 5. 风险画像：四维，声明只作输入

> 工具自报的 `sideEffect` 被赋予了过高信任：第三方工具或 MCP Server 可以把危险操作描述为低风险。`sideEffect` **保留，但降级为输入**——最终风险由**受信执行层**结合能力与资源判定。

**四个维度不可压成一个「是否可逆」**：

| 维度 | 低 | 高 |
|---|---|---|
| **数据修改** | 读、写可回滚的副本 | 删库、覆盖无备份 |
| **信息读取与外发** | 读工作区 | 读凭据、发网络 |
| **费用** | 免费本地操作 | 付费 API、云资源 |
| **代码执行与权限** | 纯计算 | 执行命令、加载原生库、申请新能力 |

```
   effectiveRisk = max(工具声明的, 宿主评估的)
```

- **`reversible` 是「数据修改」维度内的属性，不是全局维度**——且只有配合**旧内容保存 + 回滚条件**才算成立。「有 diff 所以可逆」不够：diff 需要被保存、需要能应用回去。
- **第三方工具与远端 MCP 行为未知 → 按保守等级处理**：未声明的维度不得视为无风险。
- **读凭据不是低风险**：`fs.read` 声明 `none` 也可能踩到「信息读取与外发」维度。

### 5.1 审批绑定冻结后的具体动作 ⭐（ADR-0010）

「用户批准了 A，执行的却是 B」的典型路径：中间件 `mw.beforeToolInvoke` 在批准之后改参数。

**审批对象（`ActionDigest`）至少包括**：

| 项 | 说明 |
|---|---|
| 执行主体 | 宿主附加的 `Principal`（用户/项目/Agent/Run 组合） |
| 目标节点 | 动作在哪台设备执行 |
| 工作区 / 资源身份 | 规范化路径 + 内容哈希；平台支持时用文件 ID/句柄 |
| 工具及实现版本 | `toolId@version` + provider 版本 |
| 规范化参数 | 排序、去重、路径归一后的摘要 |
| 命令相关项 | cwd、环境变量白名单、stdin 摘要 |

**规则**：

- **参数或目标变化 → 旧审批失效**，重新跑策略；需要人工时重新审批。
- **执行前复核**：权限是否撤销、审批是否过期、实际资源是否与批准时一致。
- **路径字符串的摘要不能替代真实资源校验**——执行前重新解析并比对资源身份，不长期持有句柄（审批窗口可达 30 分钟，句柄在多数平台撑不住）。

---

### 5.2 辅助模型审批的规则（关键约束）

> 你提到的「小模型审批权限」——**它不是 Agent，是一个受约束的判定器**。给它划清边界，才能既省事（无需人盯每一个低风险动作）又不失控。

**允许**：
- 批准**低风险、可回滚**的动作（如工作区内读文件、有备份与回滚条件的写）。
- 在策略给定的阈值内做**批量/自动**批准。

**禁止（由运行时骨架强制，不可被插件覆盖）**：
- **不可批准高风险动作**（删除、转账、发布、执行任意命令——必须人）。
- **不可否决人类的批准**（人已批的，它不能撤回）。
- **不可提升自身权限**（不能批准给插件新能力的动作）。
- **不可作为唯一决策者**处理高风险动作——只能「升级给人」。

**fail-safe**：
- 审批**超时未决** → `Expired` → 视为 `denied`（`I-6-3`）。
- 辅助模型**判定不确定** → 默认**升级给人**，而非默认放行。

```
   动作 ──▶ 风险画像（数据修改 / 读取与外发 / 费用 / 代码执行与权限）
              │
      ┌───────┼─────────────────────┐
      │       │                     │
   低风险   中风险                高风险（任一维度高）
   辅助模型  辅助模型可批         只能人类批
   可自动批  or 升级给人          （小模型无权）
              │
        不确定？──▶ 升级给人（fail-safe）
```

## 6. 审批交互（内嵌 UI）

- 审批弹窗是**应用内模态层**（`region.modal`），非独立窗口（ADR-0006）。
- 提供：动作摘要（`ActionDigest`）、**四维风险画像**、影响范围、风险理由、**一键批准/驳回/永远允许此类**。
- **超时策略**：每个审批有死线（如借鉴 pi-desktop 的 30 分钟），超时即 `Expired`→拒绝。
- **批量的克制**：「永远允许此类」本身是一条新策略规则的**提议**，需人确认后落库（属于用户的显式管理操作，不能由模型提议后自动生效）。
- **核对界面**（`AwaitingReconciliation`）：给出目标、调用时间、已有证据，帮助用户判断「结果未知」的那次操作到底成没成。

---

## 7. 审计

- 每个动作：能力校验、策略决策、审批结果（含 `actionDigest` 与 `Principal`）、执行结果，全链留痕（事件）。
- 可回答：「谁（人或哪个模型）在何时、基于什么规则、批准了**哪一个具体动作**」。
- **关键事件只能由所属模块产生**，生产者身份由宿主附加；插件不得伪造审批/预算/策略事件（`#8`）。
- 审计是**只读**的——审计流不可被插件改写。

---

## 8. 提示注入防御（头号威胁）

> 当 Agent 有工具权限时，注入的危害从「说错」升级为「做坏」。

- **一切外部内容不可信**：工具返回、检索结果、网页、MCP 输出 —— 都当作**数据**，不是**指令**。
- **来源标签不够，需要信任等级**：仅给内容贴「来自网页」的标签，无法回答「这个写操作是不是被网页诱导的」。因此：
  - 每段外部内容带**信任等级**（用户输入 > 本地文件 > 工具返回 > 检索结果 > 网页/MCP）；
  - 信任等级**随内容流动**：进入摘要、进入记忆时**不得丢失**（`I-7-5`）；摘要若丢弃来源，必须在结果上标注「来源已合并，等级取最低」；
  - **最终权限约束独立于模型对来源的解释**——即无论模型怎么理解这段内容，动作仍要过策略，且策略对「低信任来源参与形成的动作」可以施加更严的约束。
- **内容与动作分离**：模型看到的内容**不能**直接变成放行的动作——动作仍要过策略（人可以/小模型可以在此拦截）。
- **最小权限**：即便被注入诱导，未声明的能力也够不着。

> **诚实的边界**：我们**不声称**能可靠判定「某个动作是否受某段内容影响」（那需要一个污点传播模型）。我们保证的是：**权限约束不依赖那个判断**——低信任内容不能让动作获得更宽的能力，也不能让动作跳过审批。

对齐 `agent-research` 的 Magentic-UI 教训：**审批与沙箱缺一不可**——默认配置挡住了多数对抗场景，但提示注入下仍可能被利用。

## 9. fail-safe 原则汇总

| 场景 | 默认（fail-safe）行为 |
|---|---|
| 无规则命中 | 拒绝 |
| 审批超时 | 拒绝 |
| 辅助模型不确定 | 升级给人 |
| 策略引擎异常 | 拒绝（不是放行） |
| 沙箱不可用 | 拒绝执行有副作用的动作 |
| **运行中丢失安全组件** | 进入 `Degraded`，**拒绝发起新的副作用动作** |
| **启动时缺必需槽位** | 进入 `Maintenance`（诊断/安装/修复），不进入正常执行 |
| **普通插件试图放宽安全限制** | 忽略（只能收紧） |

**一句话**：**任何「不确定」都收敛到「拒绝/找人」，绝不收敛到「放行」。**

## 10. 示例规则集（编码场景，仅示例）

> 下面的 `priority` 是**层内**排序：它决定「用户/项目这一层里哪条规则先命中」。跨层仍是**取交集**（§3.4）——这些规则再高也不能覆盖宿主能力或用户的显式拒绝。

```yaml
- id: read-workspace-ok
  priority: 100
  matcher: { action: tool, tool: fs.read, path: inside(workspace) }
  effect: allow
  rationale: "读工作区内文件"

- id: write-workspace-ask
  priority: 90
  matcher: { action: tool, tool: fs.write, path: inside(workspace) }
  effect: allow                 # 仅当「旧内容已保存 + 可回滚」成立；否则应降为 ask
  rationale: "写工作区内（有备份与回滚条件）"

- id: write-outside-ask
  priority: 200                 # 高优先，覆盖上面
  matcher: { action: tool, tool: fs.write, path: outside(workspace) }
  effect: ask
  rationale: "写工作区外，需确认"

- id: shell-ask
  priority: 200
  matcher: { action: tool, tool: shell.exec }
  effect: ask
  rationale: "执行命令不可逆，默认询问"

- id: deny-secret-exfil
  priority: 300                 # 最高优先
  matcher: { action: tool, resource: matches("**/.env", "**/*.pem") }
  effect: deny
  rationale: "禁止读取密钥类文件"
```

## 11. 反模式

- ❌ **默认放行** → ✅ 默认拒绝。
- ❌ **能力声明即放行** → ✅ 声明 ≠ 放行，每次动作仍过策略。
- ❌ **让辅助模型批不可逆动作** → ✅ 高风险只能人批。
- ❌ **信任工具/检索返回内容** → ✅ 不可信输入 + 信任等级。
- ❌ **审批无超时** → ✅ 死线 + 超时即拒。
- ❌ **策略散落在工具内部** → ✅ 集中判定，统一留痕。
- ❌ **策略异常时放行** → ✅ 异常即拒绝。
- ❌ **插件用高优先级规则覆盖用户限制** → ✅ 层内排序、跨层交集，普通人只能收紧。
- ❌ **审批只记 invocation** → ✅ 绑定 `actionDigest`，改参即失效。
- ❌ **信工具自报的 sideEffect** → ✅ 四维风险画像，取 `max(声明, 宿主评估)`。
- ❌ **卸载/替换安全组件后继续跑** → ✅ `Degraded`，拒绝新副作用。
