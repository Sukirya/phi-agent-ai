## 0. 一句话

**循环 = 在预算内反复「规划 → 行动 → 观察」，直到任务完成、失败或触达上限。它不是内核的一部分，是一个可插拔的策略（`strategy.loop`）。** 内核只提供机制（总线/注册表/生命周期/机制性端口）；**运行骨架（Run/Step/事件/检查点/预算记账）由发行基线的运行时骨架插件提供**，且它是**必需槽位**——缺失则进入 `Maintenance`，不会「没有骨架还照常跑」（ADR-0009）。

---

## 1. 通用骨架

```
                  ┌─────────────────── Run（有预算、可恢复、可换端）───────────────────┐
                  │                                                                   │
    目标/上下文 ──▶│  Step 1: Planning   模型决定下一步（或完成）                        │
                  │      │  模型输出：动作（调工具）/ 回答 / 终止                         │
                  │      ▼                                                           │
                  │  Step 2: Acting     工具调用 → 策略闸门 → 沙箱执行                  │
                  │      │                                                           │
                  │      ▼                                                           │
                  │  Step 3: Observing  结果回灌上下文                                 │
                  │      │                                                           │
                  │      └──── 未完成且未超限？ ──▶ 回到 Step 1（下一轮）                │
                  │                                                                    │
                  │  每步产出事件；关键节点产出检查点；预算超限 → 终止                    │
                  └────────────────────────────────────────────────────────────────────┘
```

- **规划（Planning）**：把当前上下文送给模型，得到「下一步动作」；动作可以是调用工具、给出答复、或声明完成。
- **行动（Acting）**：工具调用**必过**策略与沙箱（见 `policy-and-approval.md`、`tools-and-skills.md`）。
- **观察（Observing）**：结果成为新的上下文输入。
- **收敛判定**：由**策略 + 预算**决定，不由模型单方面说了算（见 §3）。

> 这就是 ReAct 的骨架。但内核不内置 ReAct——它只是 `strategy.loop` 的**默认实现之一**。

## 2. 循环是可插拔策略

| 策略（`strategy.loop` 的贡献） | 做什么 | 适用 |
|---|---|---|
| **ReAct** | Thought → Action → Observation 循环 | 默认；开放任务 |
| **Plan-Execute** | 先出完整计划，再逐步执行 | 步骤可预判的任务，更省 token |
| **Reflexion** | 失败后先反思、再重试（不训练权重） | 易错任务；与 ReAct 组合 |
| **Workflow DSL** | 跑一段**预先编排**的固定流程，模型只在节点做判断 | 流程明确、要可控可评测 |
| **Tree-of-Thought** | 分支探索 + 剪枝 | 高价值难题，需严格控预算 |

**策略只消费统一的运行骨架**：上下文、模型、工具、预算、事件。它不直接碰存储、网络、UI（P2/P8）。换一种循环 = 换一个插件，不改内核、不改 Run 的领域模型。

**扩展点签名（概念）**：`LoopStrategy.run(runCtx) -> RunOutcome`；`runCtx` 提供 `assembleContext()`、`callModel()`、`invokeTool()`、`emit()`、`budget`、`checkpoint()`。

> **可恢复性约束（`#18`）**：策略**不得把关键状态藏在局部变量或异步闭包里**——那些无法进检查点。策略需要跨恢复保留的状态必须通过 `runCtx.state`（一个**可序列化**的键值区）读写，并在清单里声明 `stateSchema`。恢复入口固定为 `resume(runCtx)`：从检查点重建 `runCtx` 后重新进入 `run()`。这是「可插拔循环」与「可恢复执行」能同时成立的前提。

## 3. 终止与收敛（防失控的生命线）

> `agent-research` 与 `awesome-architecture` 的共同结论：**没有控制阀的循环，就是一台会自己烧钱、可能闯祸的机器。**

**三重硬上限（Budget，由运行时骨架强制，不由策略自觉）**：

| 上限 | 超限后果 |
|---|---|
| `maxSteps`（步数） | 终止 Run → `Aborted` |
| `maxCost`（成本，按用量计量） | 终止 → `Aborted` |
| `maxWallTime`（墙钟） | 终止 → `Aborted` |

**「硬上限」的成立条件（否则只是愿望）**——回应「调用结束后扣费保证不了不超预算」：

1. **调用前预留（reserve）**：发起模型调用前先从预算里**预留**一个额度（`BudgetReserved`），可用额度不足即**拒绝发起**，而不是「先跑完再算账」。
2. **输出上限**：每次调用必须带 `maxOutputTokens`，预留额度按它计算——预留才有上界。
3. **并发统一记账**：同一 Run 及其全部子 Run 的预留与结算**走同一个账本**；并发子 Run 各自预留，父的可用额度是所有子预留之和的约束。
4. **失败也结算**：请求失败但已产生费用时，按实际用量结算（`BudgetSettled`）。
5. **用量未知**：provider 未返回用量时，按**预留值**记账（宁可高估），并在事件里标注「估算」。

> **另外两道**：

- **重复检测**：同一工具 + 同一参数连续调用、或观察结果高度相似 → 判定「原地打转」，终止或强制变招。
- **不收敛检测**：连续 N 步无「新信息 / 无状态推进」→ 终止。

**模型不能自己判定「完成」**：这是 AutoGPT 的经典反模式。`Succeeded` 必须由**策略的可验证条件**给出（如测试通过、任务清单全勾、结构化输出合法），或由人确认。模型的「我认为完成了」只作为**候选**，不是终态。

```
   模型说「完成」──▶ 是否是可验证的完成条件？
                        │ 是 ──▶ 校验通过才 Succeeded
                        └ 否 ──▶ 继续 / 升级给人
```

> **为什么由运行时骨架强制而不是策略自觉**：策略是可插拔的第三方插件，不能指望每个都自律。预算在**每次模型调用与工具调用处**预留并检查，超限直接中止——这是**必需槽位**的一部分，缺席即 `Maintenance`。

## 4. 工作流 vs 自主 Agent（先做这个判断）

> Anthropic《Building Effective Agents》的核心建议：**能用确定的工作流解决，就别上自主 Agent。** 可预测性是工程美德。

```
   任务步骤基本固定、可预先编排？
     │
     ├─ 是 ──▶ 【Workflow DSL】固定流程，模型只在节点判断
     │         ✓ 可预测、好调试、便宜、好评测  ← 大多数任务到此为止
     │
     └─ 否（开放、必须随机应变）
              │
              ▼  【自主 Loop】+ 装满刹车（预算/策略/沙箱/审批/检查点）
```

**编码场景的判断**（Q4）：改一个已知 bug、跑测试、格式化 → 工作流；「读懂这个模块并重构」→ 自主循环。

## 5. 失败处理：反思再试（Reflexion）

失败时不要盲目重试同一路径。策略可实现：

```
Step 失败/结果为负 ──▶ 反思：为什么失败？缺什么信息？换个什么做法？
                       │
                       ▼
                  把「失败 + 反思」作为上下文的一部分，再进入下一轮
```

约束：反思本身也耗预算；反思次数上限（如 ≤ 2），超了升级给人。**反思不改模型权重**（Reflexion 的本义）——它改的是上下文。

---

## 6. 每步的上下文组装

循环不自己拼上下文，而是调用 `context.contributor` 链（见 `context-and-memory.md`）：

```
Step 输入 = 系统提示 + Agent 定义 + 技能注入 + 会话历史(压缩后) + 检索结果 + 上一步观察 + 剩余预算提示
```

> 上下文是循环最容易「爆」的地方：塞太多贵且糊，塞太少缺依据。分层 + 压缩是刚需，细节在 `context-and-memory.md`。

## 7. 多 Agent 编排（`strategy.orchestration`）

> 从单 Agent 起步；任务复杂到「一个角色扛不动」时再拆多 Agent（`agent-research` 与业界共识）。

| 编排 | 形态 | 适用 |
|---|---|---|
| **Supervisor/Worker** | 一个主 Agent 拆任务、派给子 Agent、汇总 | 可切分的并行任务 |
| **Group-Chat** | 多角色（规划者/执行者/审查者）围绕任务对话 | 需要多视角（借鉴 AutoGen 的 GroupChat，**但不基于已归档的 AutoGen 构建**） |
| **Pipeline** | 固定顺序的角色流水线 | 流程确定、质量要求高 |

**执行树与约束**（由运行时骨架强制）：

- **一个 Turn 至多一个活跃的根 Run**（`parentRunId` 为空）；子 Run 经 `parentRunId` 组成**执行树**，保留来源 `turnId` 关联，但**不新建用户轮次**（`I-3-5`）。
- **独立上下文**（不继承父的全部历史）+ **独立预算**（父从自己的预算里切一块给它，走同一账本）。
- **深度上限**（子不能再无脑生子）+ **扇出上限**（并发子数）。
- **结果以摘要回灌**主线，不把子 Agent 的全部轨迹塞回父上下文。
- 子 Agent 的副作用同样过策略与沙箱——**多 Agent 不放大权限**。
- **取消传播**：根 Run 进入终态（含 `Aborted`）后，有界宽限期内**强制取消全部后代**——不留无人管理的执行（`I-3-6`）。取消必须传达到模型请求、CLI 子进程与孙 Run。
- **工作区规则**：子 Agent **默认只读**；需要并行写时使用**独立工作树**，由主流程合并。多个 Agent 同时改同一文件不在 v1 支持范围。

```
  父 Run（根） ──切预算──▶ 子 Run A（独立上下文，只读工作区）
        │      ├──────────▶ 子 Run B（独立上下文，并发）
        │      └◀──摘要──── 汇总，继续主线
        └─ 终态 → 宽限期 → 取消所有后代
```

**编排的承载单位是 Task**（ADR-0008）：父 Task 派生子 Task / 子 Run，形成**任务树**；深度与扇出均有上限。

> **v1 的范围**：以上**架构预留**在 v1 就位（执行树字段、`strategy.orchestration` 扩展点、不变量、取消传播），但**多 Agent 实现不作为 v1 硬门槛**——先做单层主从，再扩展。见 `80-roadmap/evolution.md`。

> **多 Agent = 分布式 + 扇出放大**（`awesome-architecture` 的硬骨头叠加）。控制扇出与深度，否则成本与延迟指数上涨。

## 8. 检查点与恢复

- 检查点策略：每 N 步 / 关键动作前（不可逆操作前必做）/ 跨端前。
- 检查点内容：Run 状态 + 上下文快照 + 已执行步骤摘要 + 预算消耗 + **策略的可序列化状态**（`runCtx.state`）+ **固定版本**（工具/技能/循环插件）。
- 恢复：从最近检查点续跑；崩溃/断电/换端都走这条路（见 `50-distributed/handoff.md`）。
- **版本变化必须显式报告**：恢复时若 `pinnedVersions` 与当前不一致，不静默续跑（`I-3-7`）。

### 8.1 恢复与重复副作用（按工具能力决定）

「记录已执行」在「执行成功但记录未落盘」的窗口里不可靠。按能力分档：

| 能力或状态 | 恢复行为 |
|---|---|
| 外部系统支持**幂等键** | 用同一个键重试同一次逻辑操作 |
| 外部系统支持**查询执行结果** | 先查结果，再决定是否重试 |
| 可以**证明操作未执行**（进程未启动 / 前置校验失败） | 重新校验授权后重试 |
| 可能已执行、无法查证且非幂等 | 标记 `OutcomeUnknown`，Run 进入 `AwaitingReconciliation`，**暂停依赖它的后续动作** |

- **核对界面**必须给出目标、调用时间、已有证据，帮助用户判断实际结果。
- **不能统一自动重试**：普通 shell 命令、发送/发布操作无法保证「自动恢复且绝不重复」——文档承认这个边界，而不是假装能兜住。
- **检查点选在「无进行中副作用」的边界**，减少重放面。

> 对齐 `agent-research` 的 Saga/幂等建议，并修正其盲区：幂等是**前提**，不是**保证**；没有幂等键的外部操作必须有「未知」态。

### 8.2 取消传播契约

「把 Run 标成 Aborted」不等于「停止实际执行」。取消必须逐层传达：

| 目标 | 取消动作 |
|---|---|
| 进行中的模型请求 | 中止流式连接；记录已产生的用量 |
| 进行中的工具调用 | 通知执行器；能中止则中止，不能则标记「进行中，结果可能产生」 |
| CLI 子进程 | 终止进程树（含孙进程） |
| 子 Run / 孙 Run | 递归取消，受宽限期约束（`I-3-6`） |
| 无法取消的操作 | **返回「停止确认」**：说明哪些已停、哪些仍在进行、可能产生什么副作用 |

`Aborted` 事件必须携带「停止确认」结果，而不是只写一个状态。

## 9. 反模式（AutoGPT 清单，逐项堵住）

- ❌ **上下文无限膨胀** → ✅ 分层 + 压缩 + 预算。
- ❌ **模型自我判定完成** → ✅ 可验证的完成条件。
- ❌ **成本无界** → ✅ 三重硬上限（运行时骨架强制 + 调用前预留）。
- ❌ **递归不收敛** → ✅ 重复检测 + 不收敛检测 + 反思次数上限。
- ❌ **子 Agent 无深度上限** → ✅ 深度/扇出上限。
- ❌ **根 Run 结束了后代还在跑** → ✅ 宽限期 + 递归取消（`I-3-6`）。
- ❌ **恢复后一律自动重试** → ✅ 按能力分档；未知则 `OutcomeUnknown` + 待核对。
- ❌ **「已终止」就等于「已停止」** → ✅ 取消传播 + 停止确认。
