# 0001. 采用「微内核 + 插件」架构

- 状态：已接受
- 日期：2026-11-08
- 决策者：Sukirya

## 背景

核心要求是「扩展性极强：一个模块随时可被删改或添加」。候选有两条路：编译期用 feature flag 裁剪的单体，或运行时的微内核 + 插件。前者「删模块 = 重编译」，且模块间易隐式耦合，难以真正做到「删掉任意模块系统仍能跑」。

## 决定

内核只保留最小且稳定的机制——事件总线、注册表、生命周期、基础端口（存储/传输/时钟/ID/日志）。**所有领域功能（Agent 循环、工具、技能、记忆、模型、策略、UI…）都以插件形式注册进内核。**

## 取舍

- 选 A（微内核）：获得真正的可增删、可热插拔、可被第三方扩展；代价是引入注册表/生命周期/间接层，开发复杂度略升。
- 弃 B（可裁剪单体）：实现更简单、更快，但**从根上不满足**第 1 号要求，且「可移除性」无法作为验收标准。
- 用「内核 API 预算」（内核公开接口表面积设上限，超出需 ADR）来控制 A 的主要代价——内核膨胀。

## 后果

- 「可移除性」（原则 P10）成为一票否决的验收测试，需配套 Null 实现与 CI 冒烟测试。
- 一切新功能的默认路径是「写插件」，而非「改内核」；这是对开发者的持续纪律要求。
- 内核的稳定性成为一等公民：内核接口变更要走版本化（P9）与 ADR。
- 后续所有子系统文档都建立在「一切皆插件」这一前提上。
