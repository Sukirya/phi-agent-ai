# 0008. 引入可选的「任务 Task」作为顶层目标（B-lite）

- 状态：已接受（2026-11-08 修订：Task 语义收紧，见文末）
- 日期：2026-11-08
- 决策者：Sukirya

## 背景

原领域模型只有 `Session`（交互上下文）与 `Run`（一次执行），「任务」被并进 Run。问题：Run 是技术意义上的**一轮循环**，太细，当不了「目标」——无法承载「指派给某台设备/某个人」「跨多次会话继续」「多个 Agent 协作同一目标」这类需求。而本项目明确要「多端协同 + 多 Agent 协作 + 预留团队」，这三者都需要一个「目标」单位。

## 决定

引入**可选的** `Task`（顶层目标，聚合根），位于 Session / Run 之上：

- `Session` 与 `Run` 的语义**不变**。
- `Task` 关联 `0..*` Session，拥有 `1..*` Run；`Run` 归属一个 Task（显式，或**隐式默认 Task**）。
- 随手一问 → 不建 Task（走隐式默认）；跨会话 / 要指派 / 要协作 → 显式建 Task。
- Task 是**协作、指派、换端、看板**的单位；支持任务树（`parentTaskId`，设深度上限）。

## 取舍

- 选 B-lite：支撑跨会话目标、多端指派、多 Agent 协作与看板；代价是多一层实体、模型变重，且中英文命名易混淆（固定术语 **Task / Session / Run**）。用「可选 + 隐式默认」把「随口一问」的仪式降到零。
- 弃 A（不引入 Task）：最简单，但长期任务/协作/指派没有抓手，R1（换端）、R3（团队）会被迫事后把单位硬塞进来，代价更高。
- 弃全量 B（每次都有 Task）：让「一次对话解决一个目标」也背上 Task 包袱，过度设计。

## 后果

- `20-domain/domain-model.md` 新增 Task 聚合（§3.0）与 Task 事件；`context-map.md` ② 更名为「会话、任务与运行」；`glossary.md` 增补 Task 术语。
- 多 Agent 编排、换端、团队看板均以 **Task** 为承载单位。
- 任务树需深度上限（防多 Agent 递归失控）；`Archived` 的 Task 不可再指派/新增 Run。

---

## 修订（2026-11-08）：Task 语义收紧

原始决定留下两处自相矛盾，现修正：

1. **「可选」的层级说错了。** 原文说 Task 与「隐式默认 Task」二选一，但领域模型又要求「每个 Run 必属一个 Task」，而 Run 字段与 `RunScheduled` 事件都没有 `taskId`。修正为：

   - **数据上恒在**：每个 Run **必须**有 `taskId`，`RunScheduled` 事件携带 `taskId`。
   - **界面上可隐式**：「可选」只表示用户**无需**先命名、建卡片、操作任务界面。
   - **不使用全局默认 Task**：改为一事一 Task——在**首个 Run 被调度时惰性创建**一个隐藏 Task（纯聊天、纯问答不创建，避免堆积空 Task 垃圾）。
   - 用户明确「继续某个任务」时可跨 Turn、跨 Session 沿用；**模型不得静默合并两个任务**。

2. **基数与创建时序冲突。** 原文写 Task「拥有 `1..*` Run」，又要求 Task 总先于 Run 成立。修正为：Task 拥有 **`0..*` Run**，允许**先建目标、后执行**。

其余不变。

因为迟于 ADR-0009 之前讨论、但结论与之一致，本修订不新增 ADR：它只是把原决定落到可实现的形式。
