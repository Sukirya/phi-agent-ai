# 0003. 共享内核采用 Rust，外壳采用 TypeScript

- 状态：已接受
- 日期：2026-11-08
- 决策者：Sukirya

## 背景

桌面 / 移动 / 服务端需要**共享一套内核与领域逻辑**（F2）。这是全项目最难逆的决策之一。现有脚手架是 Tauri 2 + Solid(TS) + Rust（`src-tauri`）。候选：Rust 内核、全 TS、分层混合。

## 决定

- **内核 + 领域逻辑用 Rust**：一套 Rust 内核经 Tauri 2 覆盖桌面与移动，服务端是同一内核编译的原生二进制。
- **外壳（UI）用 TypeScript + Solid**：现有脚手架即此；UI 通过统一传输（Tauri IPC / WebSocket / HTTP）连任意节点。
- **插件以 TypeScript 为主**（见 ADR-0005）：内核内嵌 JS 引擎运行 TS 插件，性能敏感处由插件自带原生 CLI 兜底。
- 跨语言边界收敛到**一处**：外壳与内核之间由「命令契约 + 事件流契约」定义（见 `60-frontend/multi-frontend.md`）。

## 取舍

- 选 A（Rust 内核）：一对三端最直接；性能、原生能力、单二进制分发、HTTP/SQLite/WASM 生态俱佳；与现有 `src-tauri` 一致。代价是跨语言边界（用 Tauri IPC 抹平）与团队需熟悉 Rust。
- 弃 B（全 TS）：单语言栈、迭代快，但移动端后台执行与原生能力弱、分发重（需内嵌 Node/Deno 运行时）。
- 弃 C（分层混合）：灵活但引入两套心智模型与多个跨语言边界，长期维护成本高。

## 后果

- Rust 成为主要实现语言；TS 只负责外壳与 UI 扩展。
- 内核/领域必须保持**平台无关**（P2），平台差异全部沉到适配器。
- 团队需具备或补齐 Rust 能力；这影响招聘/协作与代码评审。
- 若日后要改，成本极高（重写内核）——这是本 ADR 被标记为「难逆」的原因。
