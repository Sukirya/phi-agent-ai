# 0007. 插件运行与隔离的落地选型：QuickJS 内核引擎 + UI 受控组件协议

- 状态：已接受
- 日期：2026-11-08
- 决策者：Sukirya

## 背景

ADR-0005 定了「插件以 TypeScript 为主（内核内嵌 JS 引擎）」，ADR-0006 定了「插件 UI 内嵌、分声明式/代码两档」。还剩两个落地问题：

1. **内核内嵌哪个 JS 引擎**（备选：QuickJS/rquickjs、V8/deno_core）？
2. **C 档代码 UI 如何隔离**（备选：iframe 内嵌、受控组件协议 + 虚拟树、Worker + 虚拟树）？

## 决定

1. **内核侧 TS 插件的 JS 引擎选 QuickJS（经 rquickjs 绑定）**。
2. **C 档代码 UI 采用「受控组件协议 + 虚拟树」**：插件产出视图树，外壳渲染；插件**不直接操作 DOM**。复杂/第三方渲染场景**回退 iframe 内嵌**（仍在外壳同一窗口内）。

## 取舍

**JS 引擎：**
- 选 QuickJS：体积小、启动快、可嵌入移动端——**三端一套引擎**，行为一致。代价是单线程、性能弱于 V8；**性能由自带 CLI 兜底**（ADR-0005），故可接受。
- 弃 V8/deno_core：快，但体积大、移动端不友好；若为纯性能引入，会让三端不再一致，且与「性能走 CLI」的既定策略重复。

**UI 隔离：**
- 选受控组件协议 + 虚拟树：插件**不接触 DOM**，能力面最小、最可移植、天然适配主题与响应式；外壳完全掌控渲染。代价是复杂交互的表达力受限、需设计视图树协议。
- 弃「插件直接操作 DOM」：最自由，但与 ADR-0006 的「布局归外壳、主题统一、跨端一致」冲突，且是安全黑洞。
- 保留 iframe 内嵌为**降级档**：少数需要任意渲染的场景可回退，但仍是内嵌图层，不是独立窗口。

## 后果

- 内核需集成 rquickjs，并设计「宿主能力接口」供插件调用（受能力中介，P5）。
- 需设计**视图树协议**（组件 + 数据绑定），并版本化（P9）。
- 引擎能力（QuickJS 支持度）成为插件 API 的上限：不支持的特性不得进入插件契约。
- iframe 降级档需单独的安全与性能考量，默认不启用。
- 若日后性能成为瓶颈，优先「把重活移到 CLI/服务器节点」，而非更换引擎（保持三端一致）。
