# 0006. 插件 UI 一律内嵌于外壳布局，插件不创建独立窗口

- 状态：已接受
- 日期：2026-11-08
- 决策者：Sukirya

## 背景

F5 要求插件扩展 UI 的能力足够强（对标 Minecraft 的 Mod/Plugin 广度）。一个关键岔路口是：插件能否创建**自己的独立窗口**（OS 级新窗口 / `window.open`）？还是只能**内嵌**在外壳已有的布局里？

## 决定

1. **插件 UI 一律内嵌在外壳的布局树中**；**外壳独占窗口**，插件不创建独立窗口。浮动、弹层、命令面板都是**应用内图层**（overlay / modal region），不是独立窗口。
2. **UI 扩展分两档**：**D 档声明式**（产出视图树，外壳渲染，默认、最安全、跨端自适应）与 **C 档代码 UI**（沙箱化组件代码，经宿主桥访问数据与命令，供复杂交互）。
3. **布局归外壳所有**：插件贡献的是布局树里的节点，区域划分、响应式、主题由外壳统一决定。
4. **UI 经宿主桥访问内核**：只读事件流、发命令，不直接触碰内核状态。

## 取舍

- 选 A（内嵌）：布局统一、跨端一致、主题统一、可被外壳编排与重排；插件无需为每种端重写 UI。代价是放弃「插件自己开窗」的自由。
- 弃 B（插件可开独立窗口）：更自由，但窗口生命周期、布局、主题、跨端一致性全部失控，且与「外壳独占窗口 + 多端自适应」的定位冲突。
- 选「两档」（D + C）：既保证绝大多数扩展安全、可移植、跨端一致，又给复杂 UI 留出强大档。代价是两套工具链与两条测试路径。

## 后果

- 外壳必须提供**区域（Region）+ 插槽（Slot）+ 宿主桥（Bridge）**模型，且这些 API 需版本化（P9）。
- C 档的隔离机制成为待定基础设施（见 `30-extension/plugin-system.md` §16）。
- 「插件管理/插件市场」这类界面自身也应是插件（吃自己的狗粮），验证 UI 扩展模型是否够用。
- 与 ADR-0003（Rust 内核 + TS 外壳）配合：UI 扩展点定义在 TS 侧，内核侧通过宿主桥与之通信。
