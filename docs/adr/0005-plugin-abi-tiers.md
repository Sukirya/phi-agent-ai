# 0005. 插件以 TypeScript 为主，性能敏感处自带原生 CLI（三档：声明式 / TS / 原生）

- 状态：已接受
- 日期：2026-11-08（**修订**：同日，将代码档从 WASM 改为 TypeScript）
- 决策者：Sukirya

## 背景

插件系统要对标「Minecraft 的 Mod/Plugin」的广度（F5），同时满足三端可移植（F2）、安全（P5）、可热插拔（P10）。单一 ABI 无法同时满足：纯数据最安全但做不了逻辑；原生最强但不可移植、不安全。

同时有一个**作者体验**约束：插件应当**好写**。写插件的人不该被迫学 Rust 或 WASM Component Model。**TypeScript** 是当下生态最大、上手最快、且与外壳（UI）同语言的选择——**一个语言写内核侧与 UI 侧插件**。

性能则用另一个机制解决：**性能敏感的插件可以自带一个原生 CLI（可执行文件 / 守护进程）**，由插件在自己进程外调用。

## 决定

插件分三档，外加一个「性能逃生舱」：

| 档 | 形态 | 可移植 | 隔离 | 适用 |
|---|---|---|---|---|
| **T0 声明式** | 纯数据（manifest / DSL，无代码） | ✅ 全端 | ✅ 最安全 | Agent 定义、技能、策略、UI 布局、工具 schema |
| **T1 TypeScript** | TS 编译为 JS，跑在**内核内嵌的 JS 引擎**里（UI 侧则在 webview 内） | ✅ 全端 | ✅ 引擎沙箱 + 能力中介 | 需要逻辑的工具、循环策略、检索器、自定义渲染 |
| **T2 原生** | 原生代码（进程内库 **或** 自带 CLI/守护进程） | ❌ 分端 | ⚠️ 进程内需白名单；CLI 走进程沙箱 | 需 OS 能力、或极致性能 |

**性能逃生舱（本 ADR 的重点）**：T1 插件（TS）在遇到性能瓶颈时，**可以在自己的包里附一个原生 CLI/守护进程**，通过**进程能力**（`process.exec`）调用它。这样插件逻辑仍用 TS 写，重活交给自带二进制——**性能与作者体验兼得**。

- 「自带 CLI」只允许在**桌面 / 服务端**使用；**移动端不支持**（系统限制 + 安全）。
- 调用自带 CLI 需**声明能力并经策略放行**（默认首次 `ask`）。
- CLI 作为**独立进程**运行，天然可套**进程级沙箱**（与 `provider.sandbox` 协同）——比进程内插件更易隔离。

**WASM 降级为可选档（T1′，按需再引入）**：保留给「用非 TS 语言写插件」或「需要最强进程内隔离」的场景；不作为默认路径，避免多套工具链的重量。

**选择准则（写进 review 清单）**：能 T0 就别 T1；T1 够快就别 T2；只有确需 OS 能力或 T1 实测不够快，才用 T2 / 自带 CLI。每升一档都要在清单里写明理由。

## 取舍

- 选「TS 为主」：作者体验最好、与 UI 同语言、生态最大、插件门槛最低。代价是 Rust 内核需内嵌并维护一个 JS 引擎，且 JS 比原生慢——后者正好由「自带 CLI」逃生舱化解。
- 弃「WASM 为主」（原方案）：可移植与隔离更好，但 TS→WASM 工具链不友好、作者门槛高、生态窄，与「好写」冲突。降为可选档。
- 选「自带 CLI 逃生舱」：用「插件自己打包、自己调用」的方式换取原生性能，且因是独立进程反而更好隔离。代价是平台受限（无移动端）、需要 `process.exec` 能力与策略门禁，以及「插件包里有二进制」带来的分发/签名复杂度。
- 弃「纯 TS，无逃生舱」：简单、全端一致，但性能天花板低，做重活（索引、解析、编译、大文件处理）会被 JS 引擎拖住。

## 后果

- **内嵌 JS 引擎选型**已定为 **QuickJS/rquickjs**（见 ADR-0007）。
- 能力表新增 `process.exec`（自带 CLI）与相应的**平台矩阵**（桌面/服务端可用，移动端拒绝）。
- 插件清单新增可选的 `cli:` 字段（指向自带可执行文件）。
- 分发与信任多了一层：插件包可能含二进制，签名/来源验证更重要（预留市场时）。
- 需更新：`module-map.md` §6（ABI 行）、`plugin-system.md` §3/§8/§12、`glossary.md`（插件档定义）。
