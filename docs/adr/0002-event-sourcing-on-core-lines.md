# 0002. 会话/运行主线采用事件溯源（其余用常规状态）

- 状态：已接受
- 日期：2026-11-08
- 决策者：Sukirya

## 背景

系统需要三样能力：① 多步 Agent 运行的**可回放与可审计**（`agent-research` 反复强调「多步黑盒必须 trace」）；② **换端继续**（R1）——把进行中的 run 迁移到另一节点；③ **本地优先**——离线积累、后续同步。CRUD 式直接读写当前状态很难同时满足这三样。

## 决定

在**会话/运行这条主线上**采用事件溯源：状态 = 事件日志的折叠；事件不可变、追加、可持久、可复制。**其余数据（配置等）用常规关系表。** 不追求全系统事件化。

## 取舍

- 选「混合事件溯源」：主线拿到可回放、可复制、天然支持换端与审计；代价是存储增长、读模型维护、最终一致，且需要事件 schema 版本化纪律。
- 弃「纯 CRUD」：简单直观，但换端与审计要从头另造，且难以回答「当时到底发生了什么」。
- 弃「全量事件溯源」：一致性与心智成本对整个系统过高，配置类数据无必要。

## 后果

- 需要一套**事件 schema 版本化**规则（只增不改、旧事件永可读，P9）。
- 需要**读模型**基础设施（可从事件重建）。
- 换端（R1）与同步（R2）实现难度大幅下降——迁移即复制事件 + 检查点。
- 哪些线用、哪些不用事件溯源，成为每个子系统文档要明确回答的问题。
