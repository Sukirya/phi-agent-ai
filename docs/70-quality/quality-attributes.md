---

## 0. 为什么单列一份

需求会变、功能会增删，但**质量属性**（系统要做得多好）是架构的长期约束。本文把「我们要什么程度」写成**可检验的场景**，并记录**取舍**——因为每个质量属性都是在牺牲别的属性换来的。

---

## 1. 优先级（可推翻）

| 质量属性 | 目标倾向 | 来源/理由 |
|---|---|---|
| **可扩展 / 可移除** | 极高 | 第 1 号要求，项目差异点 |
| **可移植（三端一套内核）** | 高 | F2 前提 |
| **离线可用 / 数据主权** | 高 | 定位核心 |
| **安全 / 可控** | 高 | Agent 能「动手」，必须能刹车 |
| **可观测 / 可回放** | 中高 | 多步黑盒，无 trace 不可调试 |
| **性能（延迟/吞吐）** | 中 | 单机优先，够用即可；重活可下沉 |
| **易用性** | 中 | 取决于最终形态 |

---

## 2. 质量属性场景（可检验）

> 场景格式：**刺激 → 响应 → 度量**。每条都要能转成一个测试或一条 review 项。

### QAS-1 可移除性（最高优先）
- **刺激**：移除**可选模块** M（注销其插件）/ 移除**必需槽位**的实现。
- **响应**：可选模块 → 不依赖它的功能照常，依赖它的功能**明确不可用**或按契约安全降级；必需槽位 → 进入 `Maintenance`/`Degraded`，**有副作用动作被拒绝**（ADR-0009 §4/§5）。
- **度量**：冒烟矩阵覆盖「可选模块 × 启用/禁用」两态 +「必需槽位缺失 → `Maintenance`」+「运行中移除安全组件（策略/沙箱/审批）→ 拒绝新的副作用动作」（`module-map.md` §5）。
- **不允许**：「沙箱缺席 → 无隔离跑」或「策略缺席 → 默认允许」。安全能力缺失一律拒绝，不降级为放行。
- **机制**：微内核 + Null 实现（诚实：写端口不得假装成功）+ 事件解耦 + 插件间无直接引用。

### QAS-2 可移植性
- **刺激**：同一内核部署到桌面 / 服务端 / 移动。
- **响应**：「一致」指**同一内核与同一契约**，**不是同一功能集**。各端须满足**平台最低能力集**：

  | 端 | 最低能力集 |
  |---|---|
  | 桌面 | 全功能（含 T2 / 自带 CLI） |
  | 服务端 | 无 UI；T2 / CLI 可用；常驻 |
  | 移动 | **T0/T1 + 无 CLI**；受系统后台执行限制 |

- **度量**：各端跑**自己的**最低能力用例（非同一组用例）；内核代码零平台 API 引用（静态检查）；移动端启动 / 挂起 / 恢复验证。
- **注明**：移动端完整产品**不是 v1 门槛**（见 `80-roadmap/evolution.md`）。

### QAS-3 离线可用 / 数据主权
- **刺激**：断网启动并使用。
- **响应**：本地会话可看、可继续（本地模型）；不依赖任何远端。
- **度量**：断网下完成「查看会话 + 本地模型对话 + 记忆检索」；无「必须联网」的阻塞路径。

### QAS-4 安全 / 可控
- **刺激**：Agent 试图执行副作用动作（含由提示注入诱导）。
- **响应**：未声明能力被拒；有副作用过策略；不可逆默认 `ask`；审批超时→拒绝。
- **度量**：注入攻击对照用例（借鉴 Magentic-UI §7.5）不得造成越权；不可逆动作 100% 有人批或策略显式放行。
- **机制**：能力中介 + 策略 + 沙箱 + fail-safe。

### QAS-5 可观测 / 可回放
- **刺激**：一次 Run 跑完（或失败）。
- **响应**：每一步（规划/工具调用/结果/决策）都有事件可回放。
- **度量**：任意 Run 可完整回放；任一副作用可追溯到「谁批准、依据哪条规则」。

### QAS-6 成本可控
- **刺激**：一次 Run 进入长循环。
- **响应**：步数/成本/超时任一超限即终止。
- **度量**：每次模型调用前有 `BudgetReserved`；可用额度不足时**拒绝发起**（而非事后计账）；并发子 Run 共享同一账本；用量未知按预留值记账。
- **注明**：只有「调用前预留」才能声称**硬上限**；事后计账只能声称事后可见。

### QAS-7 性能（够用即可）
- **刺激**：本地常见操作（发消息、看会话、检索）。
- **响应**：交互延迟在可接受范围（具体阈值待定）。
- **度量**：待定；重活（索引/编译）由 CLI/服务器节点承担。

## 3. 取舍（每个都要付出代价）

| 我们选了 | 放弃了 | 代价由什么换取 |
|---|---|---|
| 微内核（可扩展） | 简单性 / 一点性能 | 间接层；换取模块可增删 |
| 事件溯源（可回放/可换端） | 存储与一致性简单性 | 事件增长 + 读模型维护 |
| 对等节点（本地优先） | 跨公网连接的简单性 | NAT 穿透复杂度 |
| 单写者（v1） | 多端同时写 | 换来无冲突、可推理 |
| 能力中介 + 策略 | 一点便捷 | 换来开放生态的安全 |
| TS 插件（好写） | JS 性能 | 由自带 CLI 兜底 |
| 内嵌 UI（一致） | 插件开窗自由 | 换来布局/主题/跨端统一 |
| 内核狭义化 + 发行基线（ADR-0009） | 内核承载 Run 骨架的直接性 | 换来内核可静态检查、安全能力缺失时结构上无法放行 |
| 安全扩展只能收紧 | 第三方对安全策略的自由度 | 换来用户授权不可被插件覆盖 |

> **原则**：每个质量属性的提升都标出它牺牲了什么（`awesome-architecture` 的基本功）。没有代价的「全都要」是幻觉。

## 5. 演进触发信号

> 借鉴 `awesome-architecture/tutorial/演进触发信号.md`：什么时候该动架构。

| 信号 | 说明 | 动作 |
|---|---|---|
| 某模块无法被单独移除 | P10 失败 | 回退解耦（先修接口） |
| 内核 API 数量超标 | P1 预算告警 | 走 ADR，拒绝或合并 |
| 记忆检索 recall 下滑 | 评测告警 | 查检索/嵌入/准入 |
| 单写者成为瓶颈 | 用户要「多端同时编辑」 | 启动 R2（分区 + 逻辑单写） |
| 跨公网需求明确 | 用户要远程协同 | 启动 R2（中继/穿透） |
| 任务被设备绑死 | 用户要跨端续跑 | 启动 R1（handoff） |
| 成本失控 | 预算频繁触顶 | 加强路由/缓存/压缩 |
| 必需槽位清单随端扩展而膨胀 | 分档配置失控 | 重新划分基线 |
| 某个「可选」插件开始被其他插件硬依赖 | 事实上的必需 | 要么提升为必需槽位，要么拆接口 |
